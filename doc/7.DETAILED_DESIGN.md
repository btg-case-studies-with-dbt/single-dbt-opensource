## What this document is

This is **not** a greenfield data model. The gold layer, semantic models, and 69 governed metrics already exist and are built and passing (`doc/1.CONTEXT.md`). This document certifies that existing semantic manifest as the signed metric dictionary the rest of this program builds against, states the true grain of every semantic model, and names three real discrepancies found during certification review — it does not redesign anything.

## Platform shape (inherited, not re-decided here)

Single governed Postgres warehouse, medallion-layered (`raw_bronze` → `staging_silver` → `mart_gold`), with MetricFlow as the sole governed query surface over the gold layer. This program adds no new storage, no new compute, and no new ingestion — it consumes what already exists.

## Relationships

- `account_id` is the primary entity for all customer-grain revenue, quota, and token-usage semantic models; it is the natural key into `dim_customer`.
- `model_variant` is the primary entity for model-grain revenue/token-usage semantic models and a foreign entity in the quota and customer-grain token-usage semantic models; it is the natural key into `dim_model`.
- `source_region` and `territory` appear as denormalized categorical dimensions on the quota and model-grain marts directly (not joined at query time by MetricFlow); `dim_region` remains the canonical reference table for region metadata but is not a join dependency for these metrics.
- No new relationship, key, or conformed dimension is introduced by this program. This section restates what already exists so the Software Architect and AI Architect do not need to reverse-engineer it from SQL.

## Three things escalated, not silently fixed

Certifying the manifest surfaced three real gaps. Per the TPM runbook's "changes re-enter the gate" rule, none of these are fixed here — they're named for the owning role.

### Escalation 1: domain-tagging gap in the LLM catalog

`conversational-bi/backend/catalog_builder.py`'s `build_condensed_catalog()` (lines 129-149) hardcodes a `domain_metrics` dict mapping only 27 of the 69 metric names to a domain. Every metric not in that hardcoded list still appears in the catalog (the loop at line 158 iterates all 69 manifest metrics), but with `domain: "unknown"` (line 182) instead of its real domain. That is **42 of 69 metrics (61%)** mistagged:

- **Revenue** (21 of 32 mistagged): `ytd_net_revenue`, `ytd_gross_revenue`, `model_ytd_net_revenue`, `model_ytd_gross_revenue`, `wow_gross_revenue_change`, `wow_net_revenue_change`, `mom_gross_revenue_change`, `mom_net_revenue_change`, `model_wow_gross_revenue_change`, `model_wow_net_revenue_change`, `model_mom_gross_revenue_change`, `model_mom_net_revenue_change`, `model_wow_gross_revenue_pct_change`, `model_wow_net_revenue_pct_change`, `model_mom_gross_revenue_pct_change`, `model_mom_net_revenue_pct_change`, `model_unique_customers`, `model_monthly_total_net_revenue`, `model_monthly_total_gross_revenue`, `model_wow_customer_change`, `model_mom_customer_change`.
- **Token usage** (13 of 22 mistagged): `total_possible_minutes`, `active_minute_pct`, `p95_rpm`, `p95_tpm`, `wow_total_tokens`, `wow_total_requests`, `wow_active_minutes`, `model_wow_total_tokens`, `model_wow_total_requests`, `model_wow_mean_rpm`, `model_wow_mean_tpm`, `model_peak_to_mean_rpm`, `model_peak_to_mean_tpm`.
- **Quota** (8 of 15 mistagged): `effective_tpd`, `actual_input_tokens`, `actual_output_tokens`, `actual_peak_rpm`, `actual_peak_tpm`, `pending_requested_rpm`, `pending_requested_tpm`, `pending_requested_tpd`.

**Why this matters:** the TRD's TR12 and TR5 require the system to distinguish "unsupported domain" (customer-service) from "known metric, wrong/no domain tag." Today, 42 perfectly valid, governed metrics carry the same `domain: "unknown"` value a real unsupported-domain question would need to be told apart from. This also directly corrupts the PRD's domain-balanced eval set if the eval fixtures are built from this catalog's domain field.

**What the fix should be (specification, not implementation):** domain must be derived from which metrics YAML file (`metrics_revenue.yml` / `metrics_token_usage.yml` / `metrics_quota.yml`) each metric is defined in, or from an explicit domain tag added to each metric definition in the semantic layer itself — not a hardcoded list maintained separately in application code that will drift every time a metric is added. This is a Software Architect / Senior Software Engineer implementation task against this specification; the Data Architect's role here is limited to certifying that the *source of truth* for domain should be the metric definition files themselves, not a duplicated list.

### Escalation 2: `model_type` dimension meaning is unsigned

The token-usage semantic models (`token_usage_customer_monthly`, `token_usage_model_monthly`) expose a `model_type` categorical dimension. `catalog_builder.py`'s `dim_descriptions` (line 203) documents it to the LLM as `"Model type (e.g., LLM, Embedding)"` — a task-type classification. But:

- `dim_model.sql` has no `model_type` column. It has `model_task` (which could be the LLM/Embedding axis) and `is_open_source` (a boolean).
- `doc/1.CONTEXT.md`'s example dimension for models is "proprietary vs open source," which maps to `is_open_source`, not a task-type axis.

**Not resolved here.** Whether the token-usage mart's `model_type` column is populated from `model_task`, from `is_open_source` recast as a string, or from something else entirely denormalized at ingestion time is unverified in this pass — it requires reading the token-usage mart's build SQL, which is Analytics Engineer territory, not a semantic-model-definition question. **Escalating to PM/AI Architect:** confirm which value domain `model_type` actually carries before the AI Architect's NL-to-metric selector is trained or prompted to reason about it, since a wrong assumption here (e.g., assuming "LLM vs Embedding" when it's actually "proprietary vs open source") would make the selector confidently wrong rather than uncertain.

### Escalation 3: semantic model count in `doc/1.CONTEXT.md` is wrong

Corrected above (11, not 3) — flagged here as a program-doc fix, not a data change.

## Semantic layer exposure

Every consumer (Metabase, Hex, the conversational BI service, the eval runner) reads metrics through the same MetricFlow semantic layer — no metric is computed a second way by any consumer. This is unchanged and reaffirmed as the platform's core trust guarantee.

## Governance and lineage (inherited)

- Catalog/lineage: dbt's own manifest and `dbt-labs/dbt_project_evaluator` + `elementary-data/elementary` packages (already in the toolstack) provide lineage and governance checks; no new catalog tooling is introduced by this program.
- Access model: grants applied per layer via `+post-hook` to `analytics_engineer`, `data_scientist`, `business_user` roles (`doc/2.TOOLSTACK.md`), unchanged.
- Measured vs. inferred distinction: every value this program's conversational BI service returns is a **measured** governed metric value computed by MetricFlow — never an LLM-inferred or approximated number (per FR2/TR2). This structural distinction is already enforced by the "MetricFlow-only" guardrail; no additional storage-level separation is needed since the LLM never touches raw data.

## Format and schema (inherited)

Postgres tables (not an open lakehouse table format — this is a Postgres-based case study, not a Delta/Iceberg lakehouse). Schema enforcement is dbt's build-time contract/tests. No format change is in scope for this program.

## Retention and history (inherited)

- `snapshots/` capture historical change tracking for slowly-changing dimensions where configured.
- The quota semantic model is explicitly a "gapless weekly history" — retention of quota history is already a first-class design property of that mart, not something this program adds.
- No new retention requirement from the TRD; the TRD's audit-log retention question (TR9) is an application-log concern, not a warehouse-retention concern, and stays with the Software Architect.

## Architecture Tenets

- **MetricFlow is the only path to data, enforced by chokepoint, not convention.** `MetricFlowTranslator.translate()` (`query_translator.py`) is the single call site that touches the semantic layer. No other module may execute or construct a query against the warehouse.
- **A rejection must carry a specific, machine-checkable reason.** The five-outcome contract (TR12) replaces the current binary `rejection: bool`; every non-`answered` response names exactly one of four distinct non-answer categories.
- **Infrastructure failure is never a product decision, and must never be counted as one.** An LLM outage, a malformed LLM response, or a MetricFlow execution failure is `system_error`; it is categorically different from the LLM or the catalog deciding the question is unknown, ambiguous, or out of domain, and the two must never be conflated in the response, the log, or the eval numbers.
- **Server-side validation is the enforcement point, prompts are not.** Anything the LLM is only *told* to do (only select valid dimensions, only select real metrics) must be independently checked after the LLM responds and before `mf query` runs.
- **Provider selection is config-driven and swappable without code changes**, per FR8; no provider is preferred or hardcoded in the dispatch logic.
- **Fix known correctness bugs before adding capability** (TRD tenet 4): the hardcoded reference date and the broken Anthropic signature are corrected as part of this design, not deferred alongside new features.
- **A component's insides change without changing its callers.** Each module below has one responsibility and the narrowest interface that lets the others use it.

## Service Decomposition

The service is a single FastAPI process with five internal components, each already a distinct module. None of these are separate deployable services in v1 — they are decomposed as Python modules with a narrow interface, so the boundary is refactorable without becoming a distributed-systems problem the TRD's Scope explicitly declines to take on.

| Component | File | Single responsibility | Interface (what callers use) |
| --- | --- | --- | --- |
| **API layer** | `main.py` | Own the one public HTTP surface (`/`, `/health`, `/catalog`, `/query`); assemble the final `category`/response from the signals the other components emit; own request logging (TR9) | `QueryRequest` in, `QueryResponse` out (see API Contracts) |
| **Catalog builder** | `catalog_builder.py` | Convert `target/semantic_manifest.json` into the condensed `catalog_for_llm.yaml` the LLM prompt embeds; own the manifest-to-domain and manifest-to-valid-dimensions mapping | `load_manifest()`, `build_condensed_catalog(manifest) -> dict`, `resolve_metric_dimensions(manifest) -> dict` |
| **LLM client** | `llm_client.py` | Turn one NL question plus the catalog into one structured query spec, or a `system_error`/LLM-content-disposition signal; own provider dispatch | `LLMClient.query(question, model, api_key, base_url) -> dict` (see LLM Integration Boundary) |
| **Query translator** | `query_translator.py` | Own the single chokepoint that touches MetricFlow; own server-side catalog validation (`HallucinationChecker`) for both metrics and dimensions (TR2/TR3/TR7); own time-range resolution against an injectable clock (TR6) | `MetricFlowTranslator.translate(query_spec) -> dict`, `HallucinationChecker.validate(query_spec) -> list[str]`, `resolve_time_range(time_range, grain, now) -> (str, str)` |
| **Eval runner** | `eval_runner.py` | Score NL-to-metric-translation fixtures against expected specs; report accuracy separated by category per TR12/NFR | `run_eval() -> list[dict]`; consumes `LLMClient` only, never calls MetricFlow directly |

No component calls the warehouse, the LLM, or the filesystem manifest except through the interface listed. The frontend (`frontend/index.html`) is a separate deployable (static HTML/JS served by `main.py`'s `/` route) and is a client of the `/query` API contract, not a backend component.

## Runtime Topology and State Boundaries

- Single FastAPI process (`uvicorn backend.main:app`), started per the toolstack's local verification command. No worker pool, no message queue, no separate scheduler process exists in v1.
- The process is stateless between requests except for two on-disk caches it owns: `target/catalog_for_llm.yaml` (rebuilt lazily, see Decision Log) and `target/semantic_manifest.json` (owned by the dbt/MetricFlow build, read-only to this service).
- Each `/query` request is handled synchronously and independently: one LLM HTTP call, then (if applicable) one `mf query` subprocess invocation. Requests do not share in-memory state; two concurrent requests are two independent LLM calls and two independent `mf` subprocesses.
- The LLM provider is an external HTTP dependency (Ollama, an OpenAI-compatible endpoint, Anthropic, or the OpenCode Go fallback), reached over `httpx`, never held as persistent connection state between requests.
- `mf query` runs as a child process of the FastAPI process, scoped to `single-dbt-opensource/dbt` as its working directory, with `MF_SEMANTIC_MANIFEST_DIR` set explicitly — this is the only process boundary the design draws, and it exists because MetricFlow's CLI, not a library call, is the governed access surface.

## V1 Scheduler and Worker Runtime Decision

There is no scheduler and no background worker in v1. Every unit of work (one LLM call, one `mf query` call) happens inline within the HTTP request/response cycle of `/query`, synchronously, with the subprocess model already in place (`subprocess.run(...)`, blocking). This is the same decision the TRD already logs as two-way ("`mf query` subprocess-per-request execution model... not built for concurrency; acceptable only under the single-user local assumption"); this document does not reopen it, only confirms no scheduler/worker component needs to be designed to support it. If a future release needs async/queued execution (e.g., to support the later LangGraph agent loop or real concurrency), that is a new architecture decision at that time, not an extension of this one.

## State and Data Flow

This section references, and does not restate, `doc/13.DATA_ARCHITECTURE.md`'s entities, grain, and valid-dimensions table. The only state this service owns is the two caches named in Runtime Topology; all governed data — metric values, dimension values, grain — is computed by MetricFlow at query time from the gold layer and returned in the `mf query` process's stdout, parsed by `MetricFlowTranslator._parse_output()`. ## Conversational Control Flow

This is the core operation: one NL question in, one governed answer or one categorized non-answer out. Sequence, as built and as corrected by this document:

1. **Request arrives.** `POST /query` with `QueryRequest{question, model, api_key, base_url}` (`main.py`). Empty question is rejected at the transport level (`HTTPException 400`) — this is a request-validation failure, not a product category, and stays outside the five-outcome contract.
2. **Catalog is loaded.** `main.get_catalog_yaml()` returns the cached `catalog_for_llm.yaml`, rebuilding it first if `target/semantic_manifest.json`'s mtime is newer (Decision Log). Failure here (manifest missing, unparseable) is a `system_error` — the service cannot proceed without a catalog.
3. **LLM translates the question.** `LLMClient(catalog_yaml).query(question, model, api_key, base_url)` dispatches to the configured provider (LLM Integration Boundary) and returns a structured spec: metrics, group_by, grain, filters, time_range, and — after this document's TR12 fix — a `disposition` field (`answerable` / `ambiguous` / `unsupported_domain`), replacing the current boolean `rejection`.
   - If the LLM call itself fails (network error, non-2xx, timeout) or its output cannot be parsed as valid JSON matching `LLM_OUTPUT_SCHEMA`, `LLMClient` returns a distinct **infrastructure-failure marker** (not a `disposition` value) — this is what `main.py` maps to `system_error`. This is the single most important behavior change from today's code: infra failure and content disposition must arrive at `main.py` as two different shapes, not one `rejection: true` field with an ambiguous cause.
   - If `disposition == "ambiguous"` or `"unsupported_domain"`, `main.py` returns immediately with that `category`, `success: false`, and the LLM's own `disposition_reason` surfaced in `message` (never treated as a governed value — see Narration Response Contract and Isolation). No MetricFlow call is made.
4. **Server-side validation runs before any execution (TR2/TR3/TR7 chokepoint).** If `disposition == "answerable"`, the spec is passed to `MetricFlowTranslator.translate()`, whose first step is `HallucinationChecker.validate()`: every metric name is checked against the manifest's known-metric set, and — after the TR7 fix — every `group_by` and filter dimension is checked against that metric's `valid_dimensions` (from `catalog_builder.resolve_metric_dimensions()`, certified correct by the Data Architect). Any failure here returns `category = "unknown_metric"` with a `message` naming the specific unknown metric or dimension, without ever invoking `mf query`. This is the enforcement layer TR7 requires: the LLM's prompt instruction to use only valid dimensions is a hint, this check is the guardrail.
5. **MetricFlow executes.** `MetricFlowTranslator` resolves the time range (`resolve_time_range()`, now against the injected clock — TR6) and shells out to `mf query` (the sole data-access chokepoint — TR2). Non-zero exit, `FileNotFoundError`, or `TimeoutExpired` all become `category = "system_error"` (this document's fix — today `FileNotFoundError` is mislabeled `rejection: false`, `success: false`, which is inconsistent with everything else and must be corrected to `system_error` for consistency). A zero-exit, zero-row result is `category = "answered"`, `success: true`, `result.row_count == 0` (TR10 — already correct behavior in `_parse_output`, now made an explicit tested contract).
6. **Response is assembled and logged.** `main.py` builds the final `QueryResponse` from whichever step above produced a terminal signal, and appends one structured JSON-Lines log record (TR9) — question, `category`, resolved time window, selected metric(s), `cli_command`, elapsed time — with `api_key` and any credential field explicitly excluded (Security, TRD).

**Seam for the AI Architect.** Step 3's `disposition` field is exactly the plug-in point: this document defines that the field must exist, must be constrained to the three values `answerable`/`ambiguous`/`unsupported_domain`, and must be populated by the LLM call inside `LLMClient.query()` before the response leaves that component. The AI Architect's `doc/43.AI_ARCHITECT_NL_TO_METRIC_SELECTOR.md` owns the prompt strategy, model choice, and evaluation that decides *how* the LLM (or a classifier ahead of it) arrives at that value — including the exact rule for what counts as "plausibly ambiguous" — and can change that logic freely without touching this flow, as long as the three-value contract is honored. This document does not specify or guess at that rule.

## Narration Response Contract and Isolation

There is no synthesized narrative in v1 (root-cause narratives are explicitly out of scope per the PRD). The relevant isolation rule for this product is narrower but real: every free-text field this service returns — `message` (the LLM's `disposition_reason`, or a system-generated error string) and `issues` (validator detail) — is advisory, human-readable text only. It is never parsed back into the pipeline, never treated as a governed value, and never influences metric selection on a subsequent call (there is no multi-turn state in v1 for it to influence). This isolation is enforced structurally: `QueryResponse.result` (the only field carrying a governed number) is populated exclusively by `MetricFlowTranslator._parse_output()`'s parse of `mf query`'s stdout, and no code path assigns to `result` from `message`, `issues`, or any LLM-authored string. This is the same "measured vs. inferred" boundary `doc/13.DATA_ARCHITECTURE.md`'s Governance section already asserts for the platform as a whole; this document confirms the application layer does not violate it.

## The Governed-Field Read-Only Boundary

This is TR2's and TR7's enforcement point, stated as a boundary rather than a flow. Governed values (metric numbers, dimension values) are read-only from this service's perspective — the write path simply does not exist:

- **Tool:** `MetricFlowTranslator.translate()` is the only function in the codebase that constructs or executes a data-access command, and it only ever calls `mf query` (read-only by MetricFlow's own design — there is no `mf` write verb this service invokes).
- **Adoption:** every other component (LLM client, catalog builder, API layer) that needs a governed value must call `MetricFlowTranslator`, not add a second path. This is enforced by the module boundary today (no other module imports `subprocess` for a data call) and should stay enforced structurally, not just by convention.
- **Inspection:** the TRD's TR2 CI mechanism — a grep-based check in CI failing the build if `psycopg`, `sqlalchemy`, or a raw `SELECT` string appears anywhere in `conversational-bi/backend/` — is the automated tripwire for this boundary. This document specifies the check belongs in the Senior Software Engineer's CI setup, scoped to `conversational-bi/backend/**/*.py`, run on every change to that path. As the TRD notes, it is a heuristic, not proof; a failure is a prompt to inspect, not an automatic verdict.
- **Dimension boundary (TR7):** the LLM may *propose* a dimension; the only place a proposed dimension becomes part of an executed query is after `HallucinationChecker.validate()` passes it against the metric's certified `valid_dimensions` set (Conversational Control Flow, step 4). A dimension that fails this check is dropped from execution entirely (never silently substituted) and the request is categorized `unknown_metric` (Decision Log) rather than executed with a guessed dimension.

## Conversational Guardrail Escalation Detection

This section names where each of TR3/TR4/TR5's rejection triggers is detected, and draws the exact boundary between this document's scope (where the category is decided and how it is surfaced) and the AI Architect's scope (the decision rule itself):

| Category | Detected by | Detection mechanism | Owner of the decision rule |
| --- | --- | --- | --- |
| `unknown_metric` | `query_translator.HallucinationChecker.validate()` | Deterministic set-membership check: is the LLM-selected metric name in the manifest's known-metric set? Is each selected dimension in that metric's certified `valid_dimensions` set? | This document / already implemented — no external classifier needed, this is pure catalog lookup |
| `ambiguous` | `LLMClient.query()`'s `disposition` field (Conversational Control Flow, step 3) | The LLM (or a classifier ahead of it) judges the question's vocabulary maps to more than one governed metric with no disambiguating context, and emits `disposition: "ambiguous"` | **AI Architect** — the decision rule for what counts as "plausibly ambiguous" is out of this document's scope, per the TRD's explicit escalation |
| `unsupported_domain` | Same `disposition` field | The LLM judges the question is about a domain with no governed metrics (customer-service) and emits `disposition: "unsupported_domain"` | **AI Architect** — same escalation as `ambiguous` |
| `system_error` | Every component's own failure branch (LLM HTTP/JSON failure in `llm_client.py`; `mf` not found, non-zero exit, or timeout in `query_translator.py`; catalog load failure in `main.py`) | Exception/error-branch detection, never a content judgment | This document — infrastructure failure detection is an architecture concern, not a classifier concern |

The escalation boundary is precise: this document guarantees the `disposition` field exists, is constrained to three values, and is surfaced without being conflated with `system_error` on one side or `unknown_metric` on the other. It does not — and should not — specify the prompt, model, or evaluation methodology that decides when the LLM emits `ambiguous` versus `unsupported_domain` versus `answerable`; that is `doc/43.AI_ARCHITECT_NL_TO_METRIC_SELECTOR.md`'s deliverable, not yet written at the time of this document.

## LLM Integration Boundary

**Provider-selection architecture (TR8).** `LLMClient.query(user_question, model, api_key, base_url)` dispatches purely on the caller-supplied `model` string and the presence of credentials — never on a hardcoded default provider, and, per the fix below, never on an implicit fallback identity when neither is present:

- `model == "ollama"` → `_query_ollama` (local, no credentials).
- `model == "anthropic"` → `_query_anthropic` (BYOK, requires `api_key`, falling back to the `ANTHROPIC_API_KEY` environment variable only for local-dev convenience — see Defect 1 below).
- `model == "opencode"` (explicit only — new branch) → `_query_opencode_go` (local dev-auth convenience path, reads `~/.local/share/opencode/auth.json`; opt-in, never a fallback — Decision Log's `_query_opencode_go` fate entry).
- `api_key` or `base_url` supplied (any other `model` value) → `_query_openai_compatible` (BYOK, any OpenAI-compatible endpoint).
- None of the above (no `api_key`, no `base_url`, and `model` is not `"ollama"` / `"anthropic"` / `"opencode"`) → `category = "system_error"`, message names the missing credential — see Defect 2 below. This is a direct return from `LLMClient.query()` in the same infrastructure-failure-marker shape described in Conversational Control Flow step 3, not a call into any `_query_*` provider method.

The `model`-driven, credential-presence-driven selection principle is a two-way door (Decision Log); the two defects below are what this document requires fixed in that dispatch.

**Defect 1 (Anthropic signature bug).** `LLMClient.query()` calls `self._query_anthropic(prompt, api_key)` (`llm_client.py:85`) but `_query_anthropic` is defined as `_query_anthropic(self, prompt)` (`llm_client.py:210`) with no `api_key` parameter, and internally reads `ANTHROPIC_API_KEY` from the environment instead of using the key passed at request time — this silently breaks the Anthropic BYOK path for any caller supplying a key in the request body, which is exactly the request-time BYOK contract TR8 and the PR/FAQ commit to. The fix: change `_query_anthropic`'s signature to `_query_anthropic(self, prompt, api_key)` and use the passed `api_key` in the request header, matching the pattern `_query_openai_compatible` already uses (fall back to `ANTHROPIC_API_KEY` from the environment only if no `api_key` is supplied, for local-dev convenience, not as the primary path).

**Defect 2 (silent identity substitution on missing credential — this review's finding).** Today, when a caller selects a `model` that is not `"ollama"` and not `"anthropic"`, and supplies neither `api_key` nor `base_url` — e.g. a dropped/empty credential, a client bug, or simply forgetting to configure a provider — `LLMClient.query()`'s terminal `else` branch (`llm_client.py:88-90`) falls through to `_query_opencode_go`, which reads a local developer's own opencode-authenticated identity from `~/.local/share/opencode/auth.json` and queries under that credential instead of failing. The response can come back looking like a normal answer, but it ran under a completely different account than the (missing) request credential implied — this is a silent identity substitution, not a graceful default, and it violates a BYOK product's fundamental guarantee that a request runs under the credential the caller supplied, or not at all (TR8/FR8; the TRD's Security and Compliance credential-handling requirement). The fix: the terminal `else` branch returns `category = "system_error"` naming the missing credential, never `_query_opencode_go`; `_query_opencode_go` remains in the codebase but only as the explicit `model == "opencode"` branch listed above (Decision Log).

Every provider method must return the same schema (`LLM_OUTPUT_SCHEMA`, extended per the Decision Log to carry `disposition`/`disposition_reason` in place of `rejection`/`rejection_reason`), and every provider method's own exception handling must map to the infrastructure-failure marker described in Conversational Control Flow step 3 — never to a `disposition` value. This is enforced per-provider today (each `_query_*` method has its own `try/except`); the fix is only in what the `except` branch returns, not in the dispatch structure. The dispatch-level `system_error` return for a missing credential (Defect 2) uses this same marker shape directly, since it never reaches a provider method's `try/except` at all.

## Failure Isolation and Recovery Design

| Operation | Failure point | Containment | Degraded or blocking behavior | Recovery rule |
| --- | --- | --- | --- | --- |
| Catalog load | `semantic_manifest.json` missing or unparseable | Contained to `main.get_catalog_yaml()` / `catalog_builder.load_manifest()` | `category = "system_error"`, request fails cleanly with a message naming the missing/invalid file; no partial catalog is ever served | Rebuild via `dbt build` / `mf`; no automatic retry inside the request path |
| Catalog staleness | Manifest changed after last catalog build | Detected by mtime comparison (Decision Log) before the LLM call | Catalog is rebuilt inline before the request proceeds (adds one filesystem stat + rebuild latency, not a failure) | Self-healing per request; no manual step needed once the mtime check ships |
| LLM call | Provider unreachable, non-2xx, or timeout | Contained to the per-provider `try/except` in `llm_client.py` | `category = "system_error"`; underlying error message preserved in `message` and the TR9 log, never retried silently with a guessed answer | Caller (human or eval runner) resubmits; no automatic retry in v1 (not required by the TRD) |
| LLM output parsing | Invalid JSON from the LLM | Contained to `LLMClient._extract_json()`'s fallback | `category = "system_error"`; raw (truncated) LLM output preserved in the log for debugging | Same as above |
| Metric/dimension validation | LLM selects an unknown metric or an out-of-catalog dimension | Contained to `HallucinationChecker.validate()`, runs before any `mf query` call | `category = "unknown_metric"`; no MetricFlow execution attempted | Not a failure to recover from — this is correct rejection behavior (TR3/TR7) |
| `mf` CLI missing | `mf` not on `PATH` | Contained to `MetricFlowTranslator.translate()`'s `FileNotFoundError` branch | `category = "system_error"` (corrected from today's `rejection: false` — Decision Log) with an actionable message ("install dbt-metricflow") | Operator installs `dbt-metricflow`; not user-recoverable per request |
| MetricFlow query execution | Non-zero exit (bad manifest state, semantic error) | Contained to the `returncode != 0` branch | `category = "system_error"` with the stripped MetricFlow stderr excerpt | Logged with `cli_command` for root-cause tracing; not retried automatically |
| MetricFlow query latency | Exceeds the tightened subprocess timeout (Decision Log: provisional 10s) | Contained to `subprocess.TimeoutExpired` | `category = "system_error"` ("query took too long"), never a silent partial answer | Logged with elapsed time so slow-query patterns are visible in aggregate across the TR9 log |
| Zero-row governed result | Valid query, no matching rows | Not a failure — `_parse_output()` already returns an empty `rows` list correctly | `category = "answered"`, `success: true`, `result.row_count == 0` (TR10) | N/A — this is the correct, non-degraded path |

Every row above resolves to exactly one of the five TR12 categories; no failure path is left able to produce an ambiguous or unlabeled outcome. Retries are deliberately not introduced in v1 beyond what already exists (none) — a retried `mf query` against a deterministic read-only semantic layer is not unsafe to repeat, but the TRD sets no retry requirement, and adding one is a two-way door left for whoever picks up real concurrency/scale later.

## Observability, COE, and Launch Readiness

- **TR9 structured log:** one JSON-Lines record per `/query` request, written from the single `/query` handler in `main.py` (not scattered across call sites), containing: input question, `category`, resolved time window, selected metric(s), `cli_command`, and elapsed time. `api_key` and any credential-bearing field are explicitly excluded by construction — the log-writing code reads from a curated subset of fields, never serializes the raw request object, so a credential cannot leak by a future field being added to `QueryRequest` without a matching log-serializer update. A test asserting no credential-shaped value appears in any log line is the TRD's specified inspection mechanism.
- **Catalog rebuild telemetry:** each rebuild (lazy, mtime-triggered) logs its trigger reason, resulting metric/dimension count, and source manifest mtime, extending `catalog_builder.main()`'s existing print statement into the same structured log stream as TR9, so a stale-catalog incident is traceable from the same place as a query incident.
- **Launch-readiness gap found:** `/health` today only confirms the FastAPI process is up; it does not check `mf` on `PATH`, catalog freshness, or LLM reachability. Recommend `/health` report these as a status object (not enforced within this document — flagged for the Senior Software Engineer's build against this design) so an operator can distinguish "service down" from "service up but every request will 500."
- **COE traceability:** every `system_error` in the TR9 log carries enough detail (raw error, `cli_command`, elapsed time) to support a 5-Whys trace without needing to reproduce the failure — this is a direct consequence of the Failure Isolation table's rule that no failure path swallows its own error message.
