## Press Release

### Headline

AI-inference teams can now ask one question and get one governed answer across revenue, usage, and capacity.

### Sub-Headline

The new conversational BI surface routes natural-language questions through MetricFlow, so business users get fast answers without bypassing trusted metric definitions.

### Summary

Today, AI-inference platform teams operate from fragmented views of the same business. Finance looks at revenue, engineering looks at usage and capacity, customer-facing teams look at support context, and every group maintains its own dashboard or spreadsheet. When a cross-domain question comes up, such as whether a revenue drop is tied to usage, rate limits, or customer behavior, teams lose time reconciling definitions before they can make a decision.

The governed conversational BI surface gives these teams a shared way to ask business questions in natural language and receive answers backed by the existing dbt and MetricFlow semantic layer. The first version focuses on trustworthy single-metric answers across the built domains: revenue, token usage, and quota/capacity. Customer-service metrics are planned once their semantic model and governed metrics exist.

### Problem

AI-inference businesses are multi-domain by nature. Revenue depends on usage. Usage depends on model availability and quota. Quota decisions affect customers and support load. But the reporting stack usually splits those signals across teams and tools. A finance user may trust one revenue dashboard, an engineering user may trust another capacity dashboard, and support may work from tickets and spreadsheets. Even when every team is acting in good faith, metric definitions drift.

The result is slow, low-trust decision-making. A simple question can turn into multiple dashboard checks, ad-hoc SQL, and analyst follow-up. Worse, answers from different tools can disagree because the metric definitions were never governed in one place.

### Solution

The conversational BI surface answers natural-language business questions only through governed MetricFlow metrics. The LLM does not generate warehouse SQL. It maps the question to an approved metric, dimension, and time range, validates that the metric exists, and executes the query through MetricFlow.

For v1, the product deliberately does less so trust can be proven first:

- One question returns one governed metric answer.
- Revenue, token usage, and quota/capacity are supported because their semantic models and metrics already exist.
- Customer-service questions are rejected until that domain has its own governed semantic model and metrics.
- Unknown or ambiguous metrics are rejected rather than approximated. V1 deliberately rejects rather than attempts disambiguation (for example, asking "did you mean API requests or quota requests?"): a single-pass reject-or-answer product is simpler to prove trustworthy first, and disambiguation is a multi-turn conversational capability that belongs with the later LangGraph agent loop, not this v1.
- Multi-step "why did this happen?" investigations are deferred to the later LangGraph agent loop.

This gives cross-functional teams a shared answer surface without weakening metric governance.

### Leader Quote

"The hard part is not putting a chat box on top of data. The hard part is making sure the answer comes from the metric the business has actually agreed to use. This release starts there: fast answers, but only through the governed semantic layer."

### Getting Started

This repository is a local case-study prototype, not a hosted product, so "getting started" is a setup path rather than a login. A user starts the Docker Compose stack, builds the dbt project, validates MetricFlow, and opens the conversational BI app. They ask a question such as "What was total net revenue last week?" or "Show total API requests by model type this quarter." The app returns a governed answer or rejects the question if the matching metric does not exist.

Note: this setup detail is intentionally kept in the external-facing press release because there is no hosted deployment for this case study; a real customer-facing launch would replace this section with an account/login path and move build steps to internal onboarding docs.

## External FAQ

### What is this?

It is a conversational BI surface for an AI-inference platform case study. It lets users ask natural-language questions and receive answers backed by governed dbt and MetricFlow metrics.

### Who is it for?

It is for teams that share the same business data but ask different questions:

- RevOps and finance users asking about revenue.
- Engineering and capacity users asking about usage, quotas, and limits.
- Customer-facing teams that need customer-service context once that domain is modeled.

### What problem does it solve?

It reduces the time and trust gap created by siloed dashboards and inconsistent metrics. Instead of asking each team for its own number, a user asks one question against the shared governed metric layer.

### How is it different from a dashboard?

A dashboard is useful when the user knows where to look. This surface is useful when the user has a business question and needs the system to route it to the correct governed metric. It complements dashboards; it does not replace deep analysis or full BI workbooks.

### How is it different from asking an LLM to write SQL?

The LLM does not write SQL against the warehouse. It selects from governed metrics and dimensions, and the execution path goes through MetricFlow. Unknown metrics are rejected.

### Which domains are available in v1?

The built v1 domains are revenue, token usage, and quota/capacity. Customer-service is planned but not queryable until its semantic model and governed metrics are added.

### Does v1 answer "why" questions?

Not fully. V1 focuses on one natural-language question to one governed metric answer. Multi-step investigations such as "Why did net revenue drop last week?" are deferred to a later LangGraph agent loop that can branch across multiple governed metrics.

### What does it cost?

Pricing is unsigned. For this repository, the implementation is a local case-study prototype using synthetic data and bring-your-own LLM provider configuration.

### What does a user need to begin?

For the local prototype:

- Docker Compose stack running.
- dbt project built successfully.
- MetricFlow configs validated.
- Conversational BI API running.
- A configured LLM provider, either local or BYOK.

### Can it be used for real business decisions now?

Not yet. The launch gates still require a hosted-model evaluation, a domain-balanced eval suite, rejection accuracy measurement, operational runbook, latency check, and BYOK documentation.

## Internal FAQ

### Why now?

The governed semantic layer already exists: bronze to silver to gold dbt models are built, MetricFlow semantic models are in place, and 69 governed metrics exist across revenue, token usage, and quota. The next bottleneck is not metric creation; it is making those governed metrics usable by cross-functional teams without returning to ad-hoc SQL and dashboard reconciliation.

### Why not later?

If the conversational layer waits until every possible domain and investigation path is built, the product risks overbuilding before proving the hardest assumption: whether the LLM can route cross-domain natural-language questions to the correct governed metric. A narrow v1 tests that assumption directly.

### What is the v1 scope?

V1 scope:

- Natural-language question input.
- Single governed metric answer.
- MetricFlow-only execution.
- Revenue, token usage, and quota/capacity domains.
- Domain-balanced eval set.
- Rejection of unknown, unsupported, or ambiguous metrics.
- Provider-agnostic LLM configuration.

### What is out of scope for v1?

Out of scope:

- Multi-step agent investigations.
- Root-cause analysis narratives.
- Customer-service metrics before the semantic model exists.
- Raw SQL generation.
- Automatic metric creation.
- Production SaaS deployment.
- Pricing, packaging, or external launch claims.

### What is the opportunity?

The immediate opportunity is trust and speed inside cross-functional analytics workflows. The product reduces the delay between question and governed answer from minutes or hours to under 30 seconds for supported questions, while preserving semantic-layer control.

The broader opportunity is to turn governed metrics into the default interface for business questions. If the v1 routing assumption holds, the same surface can later support guided investigations and customer-facing operational workflows without abandoning governance.

### What could make this fail?

The product fails if users cannot trust routing. Cross-domain vocabulary is ambiguous. "Requests" may mean API requests, quota-limit requests, or support requests. "Usage" may mean token consumption, model utilization, customer activity, or spend. If the LLM selects the wrong governed metric, a fast answer becomes a dangerous answer.

Other failure modes:

- The eval set over-represents revenue and misses capacity/support ambiguity.
- The system answers unsupported questions instead of rejecting them.
- Relative time ranges resolve inconsistently.
- Users expect multi-step analysis from a v1 single-answer product.
- Customer-service is marketed before its semantic model exists.

### What is the make-or-break assumption?

The LLM can reliably map natural-language questions to the correct governed metric across domains with overlapping vocabulary.

Target proof: at least 95% match to MetricFlow ground truth on a domain-balanced eval set, with explicit rejection of unsupported questions.

### How will success be measured?

| Metric | Type | Baseline | Target | Instrument |
|---|---|---:|---:|---|
| Time-to-answer for supported questions | Leading | ~8-10 min estimated for a routine single-tool question, longer cross-domain (not yet directly measured) | Under 30 seconds | API timing from question submission to response |
| Metric-routing correctness | Leading | Not formally measured today | At least 95% | Domain-balanced eval set compared to MetricFlow ground truth |
| Unsupported-question rejection accuracy | Leading | Not formally measured today | TBD by the LLM-selection launch gate (`LAUNCH_GATES.md`) — signed from the same eval run that certifies routing accuracy, not before | Dedicated rejection eval category |
| Cross-domain coverage | Leading | Revenue, token usage, quota built; customer-service planned | Built domains all represented in eval set | Eval fixture inventory by domain |
| User trust in answer source | Lagging | Dashboard and analyst reconciliation required | TBD after the Forward Deployed Engineer's first real usage (loop-back milestone) — no instrument exists pre-launch to set a number against | Qualitative review or workflow telemetry, not yet instrumented |

Ground-truth labeling for the routing-correctness eval set is owned by Product (this document's owner), who signs off on the correct metric per eval question; disputes over metric meaning escalate to the Data Architect, who owns the metric dictionary.

### What claims are unsigned?

The following must not be treated as public commitments until explicitly signed:

- Pricing.
- Public launch date.
- Competitive superiority.
- ROI or productivity savings beyond the measured time-to-answer target.
- Customer quote or named customer reference.
- Production readiness.

### What must be true before production use?

Production use requires the launch gates in `single-dbt-opensource/dbt/LAUNCH_GATES.md` to pass:

- Hosted model eval meets the accuracy and hallucination bars.
- Eval suite expands beyond smoke tests and is balanced across domains.
- Rejection accuracy is measured.
- Unknown metrics are blocked before execution.
- Operational runbook exists.
- BYOK path is documented.
- Query latency is measured.

### What is the recommended next PRD focus?

The PRD should specify v1 as a governed single-answer experience. It should not specify system architecture beyond the product guardrails already approved here:

- Answers must execute through MetricFlow.
- Raw SQL generation is prohibited.
- Unknown metrics must be rejected.
- Time ranges must resolve against a real reference date.
- Provider configuration must remain pluggable.
- Customer-service remains future work until governed metrics exist.
