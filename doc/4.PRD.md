# PRD (Concise): Governed Cross-Domain Conversational BI (v1)

Status: Draft for review
Owner: Product
Date: 2026-07-02
Source inputs: `doc/5.PR_FAQ.md` (approved, commit `a07bb8b`)
Detail: see `doc/8.PRD_DETAILED.md` for functional requirement acceptance conditions, non-functional requirements, and open risks.

## Problem Statement

RevOps/finance, engineering/capacity, and customer-facing teams at an AI-inference platform each read the same underlying business reality — revenue, token usage, quota/capacity — through separate dashboards and tools whose metric definitions were never governed in one place, so a simple cross-domain question takes minutes to hours of dashboard-hopping, ad-hoc SQL, and analyst reconciliation, and different tools can disagree about the same number. V1 solves the narrowest slice of this: a natural-language question answered by exactly one governed MetricFlow metric, proving that an LLM can route reliably before any richer investigation capability is built.

## Goals

- Answer a natural-language business question with exactly one governed metric value, executed only through MetricFlow.
- Cover the three domains whose semantic models and metrics already exist: revenue, token usage, quota/capacity.
- Reject, rather than approximate, any question that does not map cleanly to a known governed metric.
- Resolve relative time ranges ("last week," "this quarter") against a real reference date.
- Keep the LLM provider pluggable (BYOK: OpenAI-compatible, Anthropic, or local) with no provider hardcoded.
- Prove the core assumption — cross-domain routing accuracy — on a domain-balanced eval set before any launch decision.

## Non-Goals

- Multi-step "why did X happen?" investigations or any agent/tool-loop behavior (LangGraph). Deferred to a later release.
- Root-cause narratives or synthesized explanations across multiple metrics.
- Customer-service questions or metrics — no semantic model or governed metrics exist yet for this domain.
- Any raw SQL generation against the warehouse, by the LLM or otherwise.
- Automatic creation or modification of metric definitions.
- Disambiguation dialogue for ambiguous questions — v1 rejects ambiguous questions in a single pass rather than asking a clarifying follow-up (see PR/FAQ Internal FAQ for rationale).
- Production SaaS deployment, multi-tenant hosting, pricing, packaging, or any external launch claim.

## Target User / Persona

- **RevOps/finance analyst** — asks revenue questions ("total net revenue last week"), currently reconciles finance dashboards with engineering's numbers by hand.
- **Engineering/capacity lead** — asks usage and quota questions ("API requests by model type this quarter," "effective RPM for account X"), currently checks Grafana/Metabase and quota history separately from revenue.
- **Customer-facing team member** — no supported question path in v1; explicitly deferred until the customer-service semantic model exists. Named here so downstream roles know this persona exists and is intentionally unserved in v1, not overlooked.

## User Stories

1. As a finance analyst, I want to ask "What was total net revenue last week?" in plain language, so that I get a governed number without opening a dashboard or pinging an analyst.
2. As a capacity engineer, I want to ask "Show total API requests by model type this quarter," so that I can see usage broken down by a dimension the semantic model already governs, without writing SQL.
3. As any user, I want the system to tell me clearly when it cannot answer, so that I never mistake a rejection for a real answer or get an approximated/wrong number.
4. As any user, I want relative time phrases to resolve consistently against today's real date, so that the same question asked on different days returns comparable, correct time windows.
5. As the program owner, I want every routing decision measured against a domain-balanced eval set, so that the 95% correctness claim is evidence, not a guess.

## Success Metrics (summary)

| Metric | Baseline | Target |
|---|---:|---:|
| Time-to-answer for supported questions | ~8-10 min estimated (not yet directly measured) | Under 30 seconds |
| Metric-routing correctness | Not formally measured today | At least 95% |
| Unsupported-question rejection accuracy | Not formally measured today | TBD by the LLM-selection launch gate |
| Cross-domain coverage | Revenue, token usage, quota built; customer-service planned | Built domains all represented in eval set |
| User trust in answer source | Dashboard/analyst reconciliation required | TBD after first real field usage |

Full metric type (leading/lagging), instrument, and ownership: `doc/8.PRD_DETAILED.md`.

## Out of Scope / Future Work

- Multi-step LangGraph agent investigations.
- Customer-service domain, once its semantic model and governed metrics exist.
- Disambiguation dialogue in place of rejection.
- Production/hosted multi-tenant deployment, pricing, and packaging.
- Any expansion of dimensions or metrics beyond what the existing semantic models already govern.

# PRD-Detail: Governed Cross-Domain Conversational BI (v1)

Status: Draft for review
Owner: Product
Date: 2026-07-02
Parent: `doc/6.PRD_CONCISE.md` — read that first for problem, goals, non-goals, personas, and the success-metrics summary. This document is the acceptance-condition and risk detail an architect builds a TRD from; it does not restate the narrative.

## Functional Requirements

| # | Requirement | Acceptance Condition |
|---|---|---|
| FR1 | Accept a natural-language question and return exactly one governed metric value with its dimensions and time range. | Given a question that maps cleanly to one known metric, the response contains the metric name, value, resolved time range, and any requested dimension breakdown, with no SQL generated. |
| FR2 | Execute every answer through MetricFlow (`mf query`); never generate or run raw SQL against the warehouse. | Every served answer traces to a logged `mf query` invocation; no code path constructs or executes raw SQL against `mart_gold` or any other schema in response to a user question. |
| FR3 | Reject questions that map to no known governed metric. | Given a question referencing an unknown or unsupported metric, the system returns an explicit rejection (not a best-guess number, not a SQL fallback) and names that the metric does not exist. |
| FR4 | Reject ambiguous questions rather than guessing or asking a follow-up. | Given a question where the vocabulary plausibly maps to more than one governed metric (e.g. "requests" matching both an API-usage metric and a quota metric) with no disambiguating context in the question, the system rejects rather than picking one or asking a clarifying question. |
| FR5 | Reject customer-service questions as out of scope. | Given a question about support tickets, CS metrics, or customer-service context, the system rejects it as an unsupported domain, distinctly from an unknown-metric rejection. |
| FR6 | Resolve relative time expressions against a real, current reference date. | Given a relative time phrase, the resolved time window is computed from the actual system date at query time, not a fixed or hardcoded date; repeated identical questions on different real dates resolve to different, correct windows. |
| FR7 | Restrict dimension use to dimensions defined in the semantic models. | Given a question implying a dimension not present in the semantic model for the resolved metric, the system rejects or omits that dimension rather than inventing one. |
| FR8 | Support provider-agnostic LLM configuration. | The active LLM provider (OpenAI-compatible, Anthropic, or local) is selected via config/environment without a code change, and at least one non-default provider can be swapped in and produce a successful answer for a smoke-test question. |
| FR9 | Log every question, routing decision (metric matched or rejection reason), and resolved time range for eval and audit purposes. | Every request produces a retrievable log record containing the input question, the routed metric or rejection category, and the resolved time window. |

## Non-Functional Requirements

*(named here for the Solutions Architect / Software Architect to quantify and design against; PM does not set the technical mechanism)*

- **Latency:** the PR/FAQ commits to under 30 seconds end-to-end for a supported question; the architect should quantify the budget across LLM call, MetricFlow query, and response rendering.
- **Accuracy/quality bar:** at least 95% metric-routing correctness on a domain-balanced eval set; rejection-accuracy target is TBD, to be signed at the LLM-selection launch gate (`single-dbt-opensource/dbt/LAUNCH_GATES.md`) using the same eval run.
- **Reliability:** no defined uptime/SLA — this is a local case-study prototype, not a hosted service. If this changes, the SRE role must set an explicit SLO before any such claim is made externally.
- **Security/compliance:** the data is synthetic with no real customer PII (`doc/1.CONTEXT.md`); no compliance regime applies to this case study as scoped. If real data is ever substituted, this NFR must be revisited before build — flagged here as an open question, not decided.
- **Auditability:** every answer must be traceable to the specific governed metric and `mf query` invocation that produced it (see FR9), so a rejected or disputed answer can be reconstructed.
- **Extensibility (seam, not built):** the architecture should leave a clean seam for adding domains (e.g., customer-service) and for the later LangGraph multi-step agent loop, without building either now.

## Success Metrics (full)

| Metric | Type | Baseline | Target | Instrument |
|---|---|---|---:|---:|---|
| Time-to-answer for supported questions | Leading | ~8-10 min estimated for a routine single-tool question, longer cross-domain (not yet directly measured) | Under 30 seconds | API timing from question submission to response |
| Metric-routing correctness | Leading | Not formally measured today | At least 95% | Domain-balanced eval set vs. MetricFlow ground truth; PM owns label sign-off, Data Architect owns metric-meaning disputes |
| Unsupported-question rejection accuracy | Leading | Not formally measured today | TBD by the LLM-selection launch gate | Dedicated rejection eval category |
| Cross-domain coverage | Leading | Revenue, token usage, quota built; customer-service planned | Built domains all represented in eval set | Eval fixture inventory by domain |
| False-rejection rate (supported questions wrongly rejected) | Leading | Not formally measured today | ≤5% — so "never wrong" can't be gamed by rejecting everything | Eval set: supported-question category, rejection flag rate |
| User trust in answer source | Lagging | Dashboard/analyst reconciliation required | TBD after first real field usage (FDE loop-back) | Qualitative review or workflow telemetry, not yet instrumented |

## Open Questions and Risks

- **Ambiguity boundary is not fully specified.** FR4 states ambiguous questions are rejected, but the exact decision rule (what counts as "plausibly maps to more than one metric") is an eval-design and prompt-design question, not a product question — escalated to the AI Architect role for the NL-to-metric selector design.
- **FR4's rejection stance is a product bet, not a neutral choice.** Over-rejection is a churn risk on par with mis-routing — if v1 rejects too many reasonable questions, users abandon it before routing accuracy is ever proven.
- **Latency budget breakdown** across LLM call vs. MetricFlow query vs. rendering is an architecture decision — escalated to Solutions Architect / Software Architect.
- **Security/compliance posture if real data is ever used** is unresolved and out of scope for this case study as currently scoped; flagged, not decided, per the NFR above.
- **Rejection-accuracy and user-trust targets are TBD**, gated on the eval run and field usage respectively (see Success Metrics table) — not blocking v1 build, but blocking the corresponding launch gates.
- **Risk:** the make-or-break routing-accuracy assumption could fail silently if the eval set is not truly domain-balanced — mitigation is the Data Architect/AI Architect jointly reviewing eval fixture coverage before the eval is trusted as evidence.
