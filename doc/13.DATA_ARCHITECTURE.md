## What this document is

This is **not** a greenfield data model. The gold layer, semantic models, and 69 governed metrics already exist and are built and passing (`doc/1.CONTEXT.md`). This document certifies that existing semantic manifest as the signed metric dictionary the rest of this program builds against, states the true grain of every semantic model, and names three real discrepancies found during certification review — it does not redesign anything.

## Platform shape (inherited, not re-decided here)

Single governed Postgres warehouse, medallion-layered (`raw_bronze` → `staging_silver` → `mart_gold`), with MetricFlow as the sole governed query surface over the gold layer. This program adds no new storage, no new compute, and no new ingestion — it consumes what already exists.

## Valid dimensions per semantic model (authoritative list for TR7)

The TRD's TR7 requires server-side dimension validation against "the semantic model," which today is only a vague pointer. This is the authoritative, exhaustive list an implementer validates against — anything not listed here for a given semantic model is not a valid dimension for metrics backed by it:

| Semantic model | Time dimension | Categorical dimensions |
|---|---|---|
| `customer_revenue_weekly` | `week_start_date` (week) | `segment`, `vertical`, `account_size`, `company_name` |
| `customer_revenue_monthly` | `month_start_date` (month) | none |
| `model_revenue_weekly` | `week_start_date` (week) | `model_family`, `model_publisher`, `source_region`, `territory` |
| `model_revenue_monthly` | `month_start_date` (month) | none |
| `customer_revenue_ytd` | `ytd_start_date` (day) | `calendar_year`, `ytd_segment`, `ytd_vertical`, `ytd_account_size`, `ytd_company_name` |
| `model_revenue_ytd` | `ytd_start_date` (day) | `calendar_year`, `ytd_model_family`, `ytd_model_publisher`, `ytd_source_region`, `ytd_territory`, `ytd_govcloud` |
| `customer_quota_weekly_history` | `quota_week_start_date` (week) | `inference_scope`, `source_region` |
| `token_usage_customer_monthly` | `tu_month_start_date` (month) | `model_type` (see Escalation 2 — meaning unsigned) |
| `token_usage_customer_weekly` | `tu_week_start_date` (week) | none |
| `token_usage_model_monthly` | `tu_month_start_date` (month) | `model_type` (see Escalation 2) |
| `token_usage_model_weekly` | `tu_week_start_date` (week) | none |

A metric's valid dimension set is exactly the dimension set of the semantic model backing it (see `resolve_metric_dimensions()` in `catalog_builder.py`, which already computes this correctly — TR7's gap is that the result isn't enforced server-side after the LLM responds, not that this mapping is wrong).

## Relationships

- `account_id` is the primary entity for all customer-grain revenue, quota, and token-usage semantic models; it is the natural key into `dim_customer`.
- `model_variant` is the primary entity for model-grain revenue/token-usage semantic models and a foreign entity in the quota and customer-grain token-usage semantic models; it is the natural key into `dim_model`.
- `source_region` and `territory` appear as denormalized categorical dimensions on the quota and model-grain marts directly (not joined at query time by MetricFlow); `dim_region` remains the canonical reference table for region metadata but is not a join dependency for these metrics.
- No new relationship, key, or conformed dimension is introduced by this program. This section restates what already exists so the Software Architect and AI Architect do not need to reverse-engineer it from SQL.

Every metric in these three files has exactly one name, one formula (`type_params`), and one home. ## Three things escalated, not silently fixed

Certifying the manifest surfaced three real gaps. Per the TPM runbook's "changes re-enter the gate" rule, none of these are fixed here — they're named for the owning role.

### Escalation 1: domain-tagging gap in the LLM catalog

`conversational-bi/backend/catalog_builder.py`'s `build_condensed_catalog()` (lines 129-149) hardcodes a `domain_metrics` dict mapping only 27 of the 69 metric names to a domain. Every metric not in that hardcoded list still appears in the catalog (the loop at line 158 iterates all 69 manifest metrics), but with `domain: "unknown"` (line 182) instead of its real domain. That is **42 of 69 metrics (61%)** mistagged:

- **Revenue** (21 of 32 mistagged): `ytd_net_revenue`, `ytd_gross_revenue`, `model_ytd_net_revenue`, `model_ytd_gross_revenue`, `wow_gross_revenue_change`, `wow_net_revenue_change`, `mom_gross_revenue_change`, `mom_net_revenue_change`, `model_wow_gross_revenue_change`, `model_wow_net_revenue_change`, `model_mom_gross_revenue_change`, `model_mom_net_revenue_change`, `model_wow_gross_revenue_pct_change`, `model_wow_net_revenue_pct_change`, `model_mom_gross_revenue_pct_change`, `model_mom_net_revenue_pct_change`, `model_unique_customers`, `model_monthly_total_net_revenue`, `model_monthly_total_gross_revenue`, `model_wow_customer_change`, `model_mom_customer_change`.
- **Token usage** (13 of 22 mistagged): `total_possible_minutes`, `active_minute_pct`, `p95_rpm`, `p95_tpm`, `wow_total_tokens`, `wow_total_requests`, `wow_active_minutes`, `model_wow_total_tokens`, `model_wow_total_requests`, `model_wow_mean_rpm`, `model_wow_mean_tpm`, `model_peak_to_mean_rpm`, `model_peak_to_mean_tpm`.
- **Quota** (8 of 15 mistagged): `effective_tpd`, `actual_input_tokens`, `actual_output_tokens`, `actual_peak_rpm`, `actual_peak_tpm`, `pending_requested_rpm`, `pending_requested_tpm`, `pending_requested_tpd`.

**Why this matters:** the TRD's TR12 and TR5 require the system to distinguish "unsupported domain" (customer-service) from "known metric, wrong/no domain tag." Today, 42 perfectly valid, governed metrics carry the same `domain: "unknown"` value a real unsupported-domain question would need to be told apart from. This also directly corrupts the PRD's domain-balanced eval set if the eval fixtures are built from this catalog's domain field.

**What the fix should be (specification, not implementation):** domain must be derived from which metrics YAML file (`metrics_revenue.yml` / `metrics_token_usage.yml` / `metrics_quota.yml`) each metric is defined in, or from an explicit domain tag added to each metric definition in the semantic layer itself — not a hardcoded list maintained separately in application code that will drift every time a metric is added. This is a Software Architect / Senior Software Engineer implementation task against this specification; the Data Architect's role here is limited to certifying that the *source of truth* for domain should be the metric definition files themselves, not a duplicated list.

### Escalation 2: `model_type` dimension meaning is unsigned

The token-usage semantic models (`token_usage_customer_monthly`, `token_usage_model_monthly`) expose a `model_type` categorical dimension. `catalog_builder.py`'s `dim_descriptions` (line 203) documents it to the LLM as `"Model type (e.g., LLM, Embedding)"` — a task-type classification. But:

- `dim_model.sql` has no `model_type` column. It has `model_task` (which could be the LLM/Embedding axis) and `is_open_source` (a boolean).
- `doc/1.CONTEXT.md`'s example dimension for models is "proprietary vs open source," which maps to `is_open_source`, not a task-type axis.

**Not resolved here.** Whether the token-usage mart's `model_type` column is populated from `model_task`, from `is_open_source` recast as a string, or from something else entirely denormalized at ingestion time is unverified in this pass — it requires reading the token-usage mart's build SQL, which is Analytics Engineer territory, not a semantic-model-definition question. **Escalating to PM/AI Architect:** confirm which value domain `model_type` actually carries before the AI Architect's NL-to-metric selector is trained or prompted to reason about it, since a wrong assumption here (e.g., assuming "LLM vs Embedding" when it's actually "proprietary vs open source") would make the selector confidently wrong rather than uncertain.

### Escalation 3: semantic model count in `doc/1.CONTEXT.md` is wrong

Corrected above (11, not 3) — flagged here as a program-doc fix, not a data change.

## Semantic layer exposure

Every consumer (Metabase, Hex, the conversational BI service, the eval runner) reads metrics through the same MetricFlow semantic layer — no metric is computed a second way by any consumer. This is unchanged and reaffirmed as the platform's core trust guarantee.

## Governance and lineage (inherited)

- Catalog/lineage: dbt's own manifest and `dbt-labs/dbt_project_evaluator` + `elementary-data/elementary` packages (already in the toolstack) provide lineage and governance checks; no new catalog tooling is introduced by this program.
- Access model: grants applied per layer via `+post-hook` to `analytics_engineer`, `data_scientist`, `business_user` roles (`doc/2.TOOLSTACK.md`), unchanged.
- Measured vs. inferred distinction: every value this program's conversational BI service returns is a **measured** governed metric value computed by MetricFlow — never an LLM-inferred or approximated number (per FR2/TR2). This structural distinction is already enforced by the "MetricFlow-only" guardrail; no additional storage-level separation is needed since the LLM never touches raw data.

## Format and schema (inherited)

Postgres tables (not an open lakehouse table format — this is a Postgres-based case study, not a Delta/Iceberg lakehouse). Schema enforcement is dbt's build-time contract/tests. No format change is in scope for this program.

## Retention and history (inherited)

- `snapshots/` capture historical change tracking for slowly-changing dimensions where configured.
- The quota semantic model is explicitly a "gapless weekly history" — retention of quota history is already a first-class design property of that mart, not something this program adds.
- No new retention requirement from the TRD; the TRD's audit-log retention question (TR9) is an application-log concern, not a warehouse-retention concern, and stays with the Software Architect.
