# TRD (Concise): Governed Cross-Domain Conversational BI (v1)

Status: Draft for review
Owner: Solutions Architect
Date: 2026-07-02
Source inputs: `doc/5.PR_FAQ.md` (a07bb8b), `doc/6.PRD_CONCISE.md` + `doc/8.PRD_DETAILED.md` (f342f0b)
Detail: see `doc/11.TRD_DETAILED.md` for full requirement acceptance/guardrail mechanisms, integrations, data requirements, security, failure-mode design, and the full decision log.

## Customer Trace

Every requirement traces to a PRD functional requirement (FR1-FR9) or a named PRD non-functional requirement. Nothing here decides product scope, metric meaning, UI, or delivery schedule — those stay with PM, Data Architect, Design Agent, and TPM respectively.

## Architecture Tenets

1. **MetricFlow is the only path to data. No exceptions, no fallback SQL.**
2. **A rejection must mean something specific.** Unknown metric, ambiguous question, unsupported domain, and infrastructure failure are four different situations; collapsing them into one bucket breaks the PRD's accuracy and false-rejection metrics.
3. **When simplicity and scale conflict for v1, ship the simpler system and flag the scale limit as a provisional assumption.** This is a local, single-user case-study prototype.
4. **Fix known correctness bugs before adding new capability.** The hardcoded reference date and the broken Anthropic provider path are pre-existing defects that violate FR6 and FR8 today.
5. **Every guardrail is a mechanism (tool + adoption + inspection), not a sentence.**

## Scope

**In scope:** a FastAPI service (`conversational-bi/backend/`) that accepts one natural-language question, translates it via an LLM into a structured query against the frozen MetricFlow catalog, validates it, executes it through `mf query`, and returns one governed answer or one categorized non-answer. Provider-agnostic LLM configuration (Ollama, OpenAI-compatible, Anthropic — BYOK). Revenue, token usage, and quota/capacity domains only.

**Out of scope (unchanged from PRD):** multi-step/agent investigations (LangGraph), root-cause narratives, customer-service domain, raw SQL generation, automatic metric creation, production multi-tenant deployment, disambiguation dialogue.

**Deployment model:** local Docker Compose, single user or a small number of sequential local users. No hosted deployment, no public network exposure. Concurrency beyond that is an open assumption, not a confirmed requirement (see `doc/11.TRD_DETAILED.md`).

| Requirement | Target |
|---|---|
| End-to-end latency | Under 30s, 95th percentile |
| Metric-routing correctness | ≥95% on domain-balanced eval |
| Rejection accuracy | TBD at the LLM-selection launch gate |
| False-rejection rate | ≤5% |
| Auditability | Every answer traceable to its `mf query` call and routing decision |
| Extensibility seam | Adding a domain or the future agent loop should not require rewriting the `/query` handler |
| Scale | Provisional: single-digit sequential local requests; no concurrency target set |

## Launch Gates

- Hosted-model eval meets accuracy and hallucination bars.
- Eval suite is domain-balanced and scores rejection categories separately from system errors.
- Unknown metrics blocked before `mf query` execution (already satisfied).
- Anthropic provider path fixed and smoke-tested before BYOK docs claim support.
- Reference-date fix verified with a clock-mocked test.
- `mf query` timeout verified to fit inside the 30s budget under real measurement.
- Operational runbook, catalog rebuild path, latency check, and BYOK docs exist.

## Open Escalations

- **AI Architect:** the ambiguity decision rule (TR4) and the false-rejection-rate eval mechanism.
- **TPM:** the scale/concurrency assumption is provisional, not confirmed — flag if the program expects otherwise.

# TRD-Detail: Governed Cross-Domain Conversational BI (v1)

Status: Draft for review

Parent: `doc/10.TRD_CONCISE.md` — read that first for scope, tenets, and the requirement summary. This document is the guardrail-mechanism, integration, data, security, and failure-mode detail an implementing engineer builds from; it does not restate the narrative.

## Functional Requirements (full)

| # | Behavior | Traces to | Done when | Guardrail mechanism |
|---|---|---|---|---|
| TR1 | Accept one NL question, return one governed metric value with resolved dimensions/time range. | FR1 | A supported question returns a single metric value, its time range, and requested dimensions in the existing `QueryResponse` shape. | N/A (core path, not a guardrail) |
| TR2 | Every answer executes through `mf query`; no code path may construct or run raw SQL. | FR2 | Static review confirms the only data-access call in the service is `MetricFlowTranslator.translate()`'s `subprocess.run(["mf", "query", ...])`. | **Tool:** a single execution chokepoint (`MetricFlowTranslator`) is the only place that touches data. **Adoption:** any new code path that needs data must call this class, not add a new one. **Inspection:** a lint/grep-based CI check that fails the build if `psycopg`, `sqlalchemy`, or a raw `SELECT` string appears anywhere in `conversational-bi/backend/`. This is a heuristic tripwire, not proof — it will false-positive on comments, docstrings, or a metric name literally appearing in a question — so treat a failure as a prompt to inspect, not an automatic verdict. |
| TR3 | Reject unknown metrics before execution. | FR3 | `HallucinationChecker.validate()` runs before any `mf query` call and returns a distinct `unknown_metric` rejection category (see TR12). | **Already implemented** as `HallucinationChecker`. Gap: the current category is generic `rejection`, not distinguished from ambiguity/domain/error — see TR12. |
| TR4 | Reject ambiguous questions (v1 does not disambiguate). | FR4 | A question whose vocabulary maps to more than one governed metric with no disambiguating context returns the distinct `ambiguous` rejection category, not a guessed metric. | **Not yet implemented.** The exact decision boundary (what counts as "plausibly ambiguous") is the AI Architect's NL-to-metric selector design, escalated per the PRD-detail's open question — this TRD only specifies that the *category* must exist and be distinguishable in the response contract (TR12); it does not specify the classifier logic. |
| TR5 | Reject customer-service / unsupported-domain questions distinctly from unknown-metric rejections. | FR5 | A question about support/CS context returns the distinct `unsupported_domain` rejection category. | Same category-distinction requirement as TR4; classifier logic is AI Architect scope. |
| TR6 | Resolve relative time expressions against the real current date, not a fixed date. | FR6 | `REFERENCE_DATE` in `query_translator.py` (currently hardcoded `datetime(2026, 6, 28)`) is replaced with `datetime.now()` (or an injectable clock for testability), and two identical questions asked on different real dates resolve to different, correct windows. | **Tool:** replace the hardcoded constant with a real-clock default and an optional override parameter (for tests only). **Adoption:** no call site may pass a literal date except test fixtures. **Inspection:** a test that asserts `resolve_time_range` output changes when the system clock is mocked forward by one day. |
| TR7 | Dimensions used in a query must come only from the semantic model governing the resolved metric. | FR7 | A question implying an unlisted dimension is rejected or the dimension is dropped, never invented. | **Partially implemented**: the LLM prompt in `llm_client.py` instructs "select only dimensions marked as valid_dimensions," but there is no server-side enforcement after the LLM responds. **Gap:** `HallucinationChecker` currently checks metric names, not dimension names against the catalog — extend it to validate `group_by` and filter dimensions the same way metrics are validated, so an LLM mistake is caught server-side, not trusted from the prompt alone. |
| TR8 | LLM provider is selected by config/request, never hardcoded. | FR8 | At least one non-default provider (e.g. a local Ollama model and an OpenAI-compatible endpoint) each produce a successful answer for the same smoke-test question via config change alone. | **Existing defect blocking this today:** `LLMClient.query()` calls `self._query_anthropic(prompt, api_key)` (`llm_client.py:85`) but `_query_anthropic` is defined as `_query_anthropic(self, prompt)` (`llm_client.py:210`) with no `api_key` parameter, and it reads `ANTHROPIC_API_KEY` from the environment instead of using the passed key — this makes the Anthropic BYOK path silently broken for any caller supplying a key at request time. **Requirement:** fix the signature so `api_key` from the request is honored, matching the pattern already used in `_query_openai_compatible`. |
| TR9 | Every question, routing decision, and resolved time window is logged for eval and audit. | FR9 | A structured log record exists per request containing the input question, the response category (answered / one of the rejection categories / system error — see TR12), the resolved time window, and the metric(s) selected, retrievable after the fact. | **Not yet implemented** — no logging currently exists in `main.py`. **Tool:** append one structured (JSON Lines) record per request to a local log file. **Adoption:** the log write happens in the single `/query` handler, not scattered across call sites. **Inspection:** a smoke test asserts a log line is written per request. API keys must be explicitly excluded from this log (see Security and Compliance). |
| TR10 | Distinguish a genuine zero-result answer from a rejection. | FR1 (implicit) | A syntactically valid, governed query that legitimately returns zero rows (e.g. a new account with no revenue yet) is returned as `success: true` with an empty result set, never coerced into a `rejection`. | **Gap found in review:** `MetricFlowTranslator.translate()` currently returns `success: true` for a zero-row `mf query` result already (confirmed in `_parse_output`), which is correct — this requirement exists to make that behavior an explicit, tested contract rather than an accidental side effect, since FR1's "one governed metric answer" must include the zero-value case. |
| TR11 | Latency budget: end-to-end response in under 30 seconds. | NFR (latency) | 95th-percentile response time for a supported question, measured by `eval_runner.py` or equivalent, is under 30 seconds. | See Non-Functional Requirements for the budget breakdown and the timeout conflict this TRD found. |
| TR12 | The response contract distinguishes four outcomes, not two. | FR3, FR4, FR5, NFR (false-rejection rate) | `QueryResponse` (or its successor) carries a `category` field with exactly these values: `answered`, `unknown_metric`, `ambiguous`, `unsupported_domain`, `system_error`. `system_error` (LLM unreachable, invalid LLM JSON, `mf` CLI missing, MetricFlow query failure, timeout) is never conflated with the three product-rejection categories. | **This is the single most important new requirement in this TRD.** The current code (`llm_client.py`, `query_translator.py`) returns `rejection: true` for both genuine product rejections and for infrastructure failures (LLM backend errors, invalid JSON, `mf` not found, subprocess timeout, non-zero `mf` exit code). Left uncorrected, an eval run or production metric would count an LLM outage as a "correct rejection" or a "false rejection" indistinguishably from a real ambiguous-question rejection, corrupting both the PRD's rejection-accuracy target and its new ≤5% false-rejection-rate target. **Tool:** a five-way category enum surfaced at every rejection point. **Adoption:** every existing `rejection: true` return site in `llm_client.py` and `query_translator.py` is re-classified into `system_error` vs. a named product category as part of implementing TR3-TR5. **Inspection:** the eval runner must report accuracy/rejection/false-rejection metrics only over `answered`/`unknown_metric`/`ambiguous`/`unsupported_domain` outcomes, with `system_error` reported separately as an infrastructure health metric, never folded into the accuracy numbers. |

## Non-Functional Requirements (full)

| Requirement | Target | Mechanism (proves it) |
|---|---|---|
| End-to-end latency | Under 30s, 95th percentile, for supported questions | `eval_runner.py` timing harness; **found conflict:** `query_translator.py` currently sets a 60-second subprocess timeout on `mf query` (`query_translator.py:224`), which alone can exceed the entire 30s budget. **Requirement:** lower the `mf query` subprocess timeout to a value that leaves headroom for the LLM call and response rendering (provisional budget: LLM call ≤15s, MetricFlow query ≤10s, rendering/network ≤2s, buffer ≤3s = 30s total) — this is a two-way door, tune the numbers once real timing data exists from the eval runner. |
| Metric-routing correctness | ≥95% on domain-balanced eval | `eval_runner.py` scored only over non-`system_error` categories (per TR12) |
| Rejection accuracy | TBD at the LLM-selection launch gate | Same eval mechanism, `unknown_metric`/`ambiguous`/`unsupported_domain` categories scored separately from `answered` |
| False-rejection rate | ≤5% of supported questions wrongly rejected | Eval set's supported-question category, scored against the `answered` vs. any-rejection-category split, excluding `system_error` |
| Auditability | Every answer traceable to its `mf query` invocation and LLM routing decision | TR9 structured log; `cli_command` field already captured in `MetricFlowTranslator.translate()` result, must be included in the log record |
| Extensibility seam (assumption, not built) | Adding a domain (customer-service) or the future LangGraph agent loop should not require rewriting the `/query` handler | The catalog-driven approach (`catalog_builder.py` derives available metrics from `semantic_manifest.json`) already provides this seam — a new domain is additive once the Data Architect adds it to the semantic manifest, requiring no code change here. This is a **two-way door**: if this assumption proves false once a real second domain is added, the seam design is revisited then, not now. |
| Scale (assumption, provisional) | Single-digit sequential local requests; no defined concurrent-user target | No mechanism yet — flagged as an open assumption per Dive Deep; if a real concurrency requirement emerges, this NFR must be re-opened with the TPM before build, not assumed away. |

## Integrations

| System | Direction | Protocol | Adapter contract | Behavior when unavailable/slow/malformed |
|---|---|---|---|---|
| MetricFlow / dbt semantic layer | Read-only | Local subprocess (`mf query` CLI) against `single-dbt-opensource/dbt` | `MetricFlowTranslator` is the sole adapter; must remain the only call site (TR2) | **Unavailable** (`mf` not on PATH): already returns a named error (`FileNotFoundError` branch). **Slow:** currently a 60s timeout, must tighten per NFR latency budget. **Malformed/query failure:** already captured (`returncode != 0` branch) and must route to `system_error`, not a product rejection (TR12). |
| LLM provider (Ollama / OpenAI-compatible / Anthropic / OpenCode Go fallback) | Read-only (question in, structured JSON out) | HTTP, per-provider (`httpx`) | `LLMClient.query()` dispatches by `model` string; each provider method must return the same schema (`LLM_OUTPUT_SCHEMA`) | **Unavailable/error:** already caught per-provider and returned as `rejection: true` — must be reclassified as `system_error` (TR12), not a product rejection. **Malformed JSON:** already handled by `_extract_json`'s fallback — same reclassification applies. **Anthropic path specifically:** currently broken (TR8) and must not be offered as a working provider until fixed. |
| Semantic manifest / catalog (`target/semantic_manifest.json`, `target/catalog_for_llm.yaml`) | Read-only, generated by `dbt build` / `mf` | Local filesystem | `catalog_builder.py` regenerates the condensed YAML catalog from the manifest if the cached file is missing | **Gap found:** the catalog is only rebuilt when `catalog_for_llm.yaml` is absent, not when the underlying `semantic_manifest.json` changes after a rebuild — a stale catalog could let the LLM select a metric that was renamed or removed. **Requirement:** rebuild the catalog when the manifest's modification time is newer than the cached catalog's, not only when the cache is missing entirely. |

## Data Requirements

- **Input contract:** `question` (required, non-empty string), `model` (optional, default provider identifier), `api_key` / `base_url` (optional, provider credentials). Mirrors the existing `QueryRequest` model; add the `category` field to `QueryResponse` per TR12.
- **Canonical definitions:** metrics and dimensions are defined exclusively by the MetricFlow semantic manifest, owned by the Data Architect. This TRD treats that manifest as a one-way door it consumes and never redefines — no new metric or dimension may be introduced by this service.
- **Nulls / missing entities:** a metric with no matching rows in the resolved time window returns a valid zero-row answer (TR10), not an error. A metric or dimension absent from the manifest is rejected before execution (TR3/TR7), never approximated.
- **Retention:** the TR9 audit log is local, append-only, and has no defined retention policy for v1 (case-study scope, synthetic data) — flagged as an open item if this moves toward a real deployment.

## Security and Compliance

- **Data classification:** synthetic data only, no real customer PII, per `doc/1.CONTEXT.md`. No compliance regime applies to v1 as scoped; revisit this section before any real-data substitution (already flagged as an open risk in the PRD-detail).
- **Credential handling (BYOK):** the current `QueryRequest.api_key` field accepts a provider API key directly in the request body. **Requirement:** the TR9 audit log must explicitly exclude `api_key` and any header/body field carrying a credential from every log record — logging the question and routing decision must never log the key. This is a mechanism gap today since no logging exists yet; it must be built in from TR9's first implementation, not retrofitted. **Inspection:** add a test asserting no request-supplied key or credential field appears in any log line, so this is a mechanism per tenet 5, not just a sentence.
- **Network exposure:** local-only, no public network exposure in v1; no additional access-control requirement beyond what Docker Compose's local network already provides.
- **Outbound calls:** the service makes outbound HTTP calls only to the configured LLM provider; no other outbound integration exists, so no additional outbound-hook control is required for v1.

## Failure Modes (Correction of Errors design)

| Failure | Detection | Degraded-but-trustworthy behavior | Root-cause traceability |
|---|---|---|---|
| LLM backend unreachable or errors | Existing per-provider try/except | Return `system_error` (not a product rejection), with the underlying error message preserved for logs | TR9 log record captures the raw error message |
| LLM returns invalid JSON | Existing `_extract_json` fallback | Return `system_error` with the raw (truncated) LLM output preserved for debugging, not silently retried with a guessed answer | Same log record includes truncated raw output |
| `mf` CLI not found | Existing `FileNotFoundError` branch | Return `system_error` with an actionable message ("install dbt-metricflow") | Logged as an environment failure, distinct from a query-content failure |
| MetricFlow query fails (bad manifest state, semantic error) | Existing non-zero-exit branch | Return `system_error` with the stripped MetricFlow error text | `cli_command` and stderr excerpt both logged |
| MetricFlow query exceeds latency budget | Currently a 60s timeout; must tighten per NFR | Return `system_error` ("query took too long"), never a silent partial answer | Logged with elapsed time so slow-query patterns are visible in aggregate |
| Catalog stale relative to manifest | Not currently detected | Rebuild-on-mtime-change (Integrations section) prevents most staleness; if it still occurs, a metric that no longer exists in `mf`'s own validation will surface as a `system_error` from the query-failure path above, not a silent wrong answer | |

## Decision Log (full)

| Decision | Door type | Choice | Trade-off |
|---|---|---|---|
| Keep MetricFlow as the sole execution path | One-way (inherited from PM/PR-FAQ, not reopened here) | No raw SQL fallback, ever | Slower to extend to ad-hoc questions, but the entire product's trust claim depends on it |
| Five-outcome response category (TR12) | One-way once the eval and any client (frontend, eval runner) depend on it | `answered` / `unknown_metric` / `ambiguous` / `unsupported_domain` / `system_error` | Slightly more response-shape complexity now; without it, the PRD's accuracy and false-rejection metrics cannot be trusted, which is the more expensive failure |
| Local-clock reference date over env-var override | Two-way | `datetime.now()` with an injectable override for tests only | Simpler than a configurable "as-of" date; revisit if a demo needs a frozen date later |
| `mf query` subprocess-per-request execution model | Two-way, revisit if scale changes | Keep the current subprocess model for v1 | Not built for concurrency; acceptable only under the single-user local assumption stated in Scope |
| Audit log as local JSON Lines file, not a database table | Two-way | Simplest mechanism that satisfies TR9/FR9 for v1 | Not queryable at scale; fine for a local case study, would need revisiting for a hosted version |
| Ambiguity/false-rejection classifier logic left unspecified here | Escalated, not this role's door to open | This TRD only requires the category exist (TR4/TR12); the decision rule is the AI Architect's | Keeps the Solutions Architect from guessing at a classifier design that belongs to a role with an evaluation methodology for it |

## Open Escalations (full)

- **AI Architect:** the ambiguity decision rule (what counts as "plausibly ambiguous" for TR4) and the eval mechanism for the ≤5% false-rejection-rate target both require the NL-to-metric selector design and evaluation this TRD deliberately does not specify.
- **Data Architect:** no new escalation — this TRD does not touch metric or dimension definitions, only consumes the existing manifest.
- **TPM:** the scale assumption (single-digit sequential local requests, no concurrency target) is a provisional assumption, not a confirmed requirement — flagging in case the program has a real concurrency expectation this TRD is not aware of.
