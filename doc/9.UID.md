# Customer Experience Narrative

A RevOps analyst opens the local app because she needs one number before a 2pm meeting: net revenue last week. She doesn't open a dashboard and doesn't ping the data team — she types the question into a single box at the top of the screen, the same box that was there the last time she used this tool and will be there the next time. She presses Enter. For a few seconds the screen tells her, in plain words, what it's doing — reading the question, matching it to a governed metric, running MetricFlow — instead of leaving her staring at a spinner. Then a calm, plainly-labeled card appears: the metric name, the number, the week it covers, the dimension she asked for. She trusts it because every governed answer from this tool looks the same, and because it never claims more than the number itself — no synthesized story, no inferred cause, just the metric MetricFlow actually returned.

If she asks something the system can't answer — a metric it doesn't know, a word that means two different things ("requests" as API calls or as quota requests), a customer-support question this tool was never built to handle, or the tool itself breaking underneath her — she gets a visibly different card that tells her so directly, in a tone that never scolds her and never dresses up a failure as an answer. If she isn't sure what to ask, one tap shows her every metric and dimension this tool actually governs, in plain language, so she stops guessing at vocabulary. Nothing about this experience competes for her attention, asks her to learn it, or pretends to be more than it is: a single box, a single governed answer or a single honest reason there isn't one, every time.

# Design Tenets

- **Honesty over confidence.** An answer looks like an answer only when it is one. A rejection never borrows the visual language of success, and a success card never hides that it came from a specific `mf query` invocation.
- **One box, one question, one truth.** The input never implies a running conversation with memory it doesn't have — v1 answers one question at a time, and the interface must not visually suggest otherwise (see Cross-Cutting Implementation Notes for where the existing frontend already breaks this).
- **Discoverable, not documented.** What the system can answer is one tap away inside the product — a metrics dictionary and a short instructions surface — not a README the person has to leave the app to find.
- **Governed, and visibly so.** Every answer shows the metric it came from; nothing is presented as a number without a traceable source.
- **Local-tool proportions.** This is a single-user, local Docker Compose prototype. No multi-user chrome, no enterprise navigation, no feature this scope doesn't need — subtraction is the default, not an afterthought.

# User Interface Details and Mockup

## Report Flow (locked — the default reading experience)

**Visual reference:** none yet. `doc/7.DESIGN_MOCK.html` is currently a blank placeholder for this program (its own header comment says explicitly not to copy the sibling product's mock and to build fresh from this UID). It should be produced from the Wireframe Notes and Key Screens below — see Mockup Links.

The default and only reading experience in v1 is: a person types one natural-language question, the system takes up to ~30 seconds to route and execute it, and the person receives exactly one of five outcomes rendered as a single card in the same position on screen every time. There is no separate "report" object to browse, filter, or version — v1 deliberately has no report history, no saved views, and no narrative synthesis (the PRD's Non-Goals explicitly exclude "root-cause narratives or synthesized explanations across multiple metrics," `doc/6.PRD_CONCISE.md`). The single most important design fact of this product is that a rejection is not a lesser or broken version of an answer — it is one of five equally first-class, equally polished outcomes.

**Hard acceptance gate:** every response the Ask Screen renders carries an explicit `category` value from the backend response contract — `answered`, `unknown_metric`, `ambiguous`, `unsupported_domain`, or `system_error` (TR12, `doc/11.TRD_DETAILED.md`). The UI must branch its rendering on this field alone, never on string-matching a message or inferring category from the presence/absence of a result. The UI must never render a rejection using the visual language (color, iconography, layout) of a successful answer, and must never render an `answered` state without its governing metric name and the `mf query` trace that produced it.

**Narrative quality bar (WBR-inspired):** not applicable to v1. This sub-section heading is inherited from a sibling product's Weekly-Business-Review-style narrative reporting UID and does not apply here — the PRD's Non-Goals explicitly rule out synthesized narrative or root-cause prose for this product (`doc/6.PRD_CONCISE.md`). Nothing on the Ask Screen should read as prose written *about* the number; it should read as the number, labeled. If a future release scopes a narrative-synthesis capability, this section should be reopened by Product before Design invents prose treatment for it — Design does not add narrative styling on its own initiative.

## Design Goals

- A first-time person reaches their first governed answer within one question, with no login, no onboarding screen, and no tutorial to get through first — they type, they get truth or an honest "no."
- A person can tell, at a glance, without reading fine print, whether they're looking at a governed answer or one of the four reasons they didn't get one — the five outcome states are visually and verbally distinct and are never confusable with each other.
- A person never has to guess vocabulary — before or after asking a question, they can find in one tap what metrics, dimensions, and phrasing this tool actually supports.
- Waiting for an answer (up to 30 seconds, per TR11) feels like the system is working, not stalled — the wait is staged and legible, never a bare spinner over dead air.
- Every rejection preserves the person's dignity and trust: it explains itself in plain language and, where possible, points toward what would work, and never reads as a raw error code or implies the person did something wrong.
- Nothing on the Ask Screen claims more than MetricFlow actually returned — no synthesized narrative, no invented interpretation dressed as fact.

## Key Screens

### 1. Report Screen (the single primary user screen)

Referred to below as the **Ask Screen** — this is the one primary screen in v1; "report" in the inherited header name is retained per the existing document skeleton, but the product has no separate report object (see Report Flow above).

- **Person and moment:** a RevOps/finance analyst or engineering/capacity lead, mid-task, who needs one governed number and doesn't want to open a dashboard. They arrive with a specific question already in mind, not to browse.
- **Single most important thing on the screen:** the question input, and — once answered — the Outcome Card directly below it. Everything else on the screen is secondary to those two.
- **Primary action:** type a question, press Enter or tap Send.
- **Must-have elements:**
  - Persistent header: product name, domain-coverage indicator (Revenue / Token Usage / Quota — the three built domains, shown so the person knows the ceiling of what's supported before they even ask), and the model/provider configuration entry point.
  - Tab bar: Ask (default) / Metrics Dictionary / Instructions (see Navigation Structure).
  - The question input bar, always present and always focused/ready — it does not disappear once an answer is shown; the person can ask their next question immediately.
  - The Outcome Card region, directly below the input, showing exactly one of: empty state, loading state, or one of the five outcome states.
  - Session history: a lightweight, append-only list of this session's past questions and their outcome category, below the Outcome Card, so a person can see what they already asked without re-reading the whole screen.
- **Empty state (before the first question):** a short, single sentence — "Ask a business question about revenue, token usage, or quota" — with one example question per built domain shown as static text (not clickable chips that would suggest more capability than exists). No illustration, no marketing copy. The domain-coverage indicator in the header is the only other content visible.
- **Loading state:** see Report Flow / Cross-Cutting Implementation Notes for the staged-progress design and the open architecture question it raises. At minimum: the input bar disables its Send action (never disables typing — a person can still edit or re-read their question while waiting), and the Outcome Card region shows a staged, textual "working" indicator, not a bare spinner.
- **The five outcome states** (each replaces the loading state in the same Outcome Card region; see UI Components → Outcome Card for full detail and the honesty rule each must follow):
  - `answered` — a calm, neutral-toned card: metric name/label, value, resolved time range, requested dimension breakdown (small table, not a chart — v1 answers are single values or short breakdowns, not time series), and the underlying `mf query` command shown collapsed/expandable for provenance.
  - `unknown_metric` — an informative-toned card (not alarm-colored): states plainly that the question doesn't match a governed metric, and invites the person to the Metrics Dictionary tab.
  - `ambiguous` — same informative tone family as `unknown_metric` but a distinct label and icon: states that the question's wording could map to more than one governed metric, without guessing which one, and invites the person to rephrase or check the dictionary. (v1 does not attempt disambiguation dialogue — this is a terminal state per question, per PRD Non-Goals.)
  - `unsupported_domain` — a neutral, boundary-toned card, distinct from both of the above: states this question is outside what the tool covers today (customer-service questions), names the domains that *are* covered, and does not imply the person made an error.
  - `system_error` — the only state permitted to use an alert tone, and even then paired with a retry action, never blame language ("the system hit a problem answering this — try again" rather than exposing raw exceptions).
- **Error state (system-level, distinct from the five product outcomes):** if the initial page load itself fails (e.g., the backend is unreachable before any question is even asked), the screen shows a full-screen, single-sentence notice with a retry action — this is a page-load failure, not a `system_error` query outcome, and must look visually distinct from both.

### Navigation Structure

A persistent tab bar, immediately below the header, with three tabs: **Ask** (default, selected on load), **Metrics Dictionary**, **Instructions**. Switching tabs never loses the Ask Screen's session history or in-flight question — the Ask tab's state persists in the background exactly as the person left it. The tab bar is the only top-level navigation in the product; there is no sidebar, no settings page separate from the existing provider/model modal, and no additional menu. This matches the local single-user Docker Compose scope: three tabs are the entire information architecture this tool needs.

### Operator / Run-Status Surfaces (separate from the report screen)

Not applicable to v1. The TRD's audit trail (TR9) is a local, append-only JSON Lines log file inspected on the filesystem for eval and debugging purposes — it is explicitly not a UI surface (`doc/11.TRD_DETAILED.md`, Data Requirements: "no defined retention policy for v1... flagged as an open item if this moves toward a real deployment"). Given the single-user local-Docker-Compose scope confirmed in the TRD's Architecture Tenet 3 ("ship the simpler system... this is a local, single-user case-study prototype"), there is no operator-facing run-status screen in v1 — building one would be adding a feature the TRD does not ask for. ### Narrative Refinement (folded into the Report Screen for Phase 1)

Repurposed for this program: this header slot, in the sibling product this document's skeleton came from, described in-line editing of a synthesized narrative. That capability does not exist in this product's v1 scope (PRD Non-Goals exclude narrative synthesis entirely). What *does* fold into the Ask Screen surface for this phase — matching the Program Plan's "Addendum: UI Tabs Feature — Metrics Dictionary and Instructions" (`doc/12.PROGRAM_PLAN.md`) — is the discoverability pair of tabs:

- **Metrics Dictionary tab.** Person and moment: someone who either got an `unknown_metric`/`ambiguous` rejection and wants to see what's actually governed, or a first-time user who wants to know the ceiling of the tool before asking anything. Single most important thing: a scannable, domain-grouped list of every governed metric with its plain-language description. Primary action: scan/search, then return to Ask with a better-informed question (no direct "ask this" shortcut in v1 — see UI Components for why). Must-have elements: grouped by domain (Revenue / Token Usage / Quota, matching the header badges exactly so the grouping is never a surprise), per-metric name, one-line description, unit/type, and its valid dimensions; a separate dimensions-glossary section for shared dimensions (e.g. `account_id__segment`, `model_variant__model_family`) since several metrics share them. Data source: the existing `GET /catalog` endpoint, which already returns exactly this shape (`domains`, `metrics[]` with `name`/`label`/`description`/`type`/`domain`/`valid_dimensions`/`valid_grains`, `dimensions[]` with `name`/`type`/`description`) — no new backend work is required for this tab's content. Empty state: not applicable (the catalog is always non-empty once dbt has built); loading state: a brief skeleton list while `/catalog` resolves (typically fast, filesystem-backed); error state: if `/catalog` fails (missing/stale `semantic_manifest.json`), a plain notice that the metrics list couldn't load, distinct in tone from any Ask Screen outcome state, since this is a tooling failure, not a question outcome.
- **Instructions tab.** Person and moment: a first-time user, before ever typing a question, or someone re-orienting after a rejection. Single most important thing: 3-5 example questions, one per built domain, phrased exactly as a person would type them. Primary action: read, then switch back to Ask. Must-have elements: how to phrase a time range ("last week," "this quarter" — and a note that these resolve against today's real date, per TR6), what happens on each of the five outcomes in one line each, and an explicit statement of what's out of scope (customer-service questions, multi-step "why" investigations) so expectations are set before the person is disappointed by a rejection. This is static content — no API call, no loading state, no error state (it ships with the frontend).

## User Flows

### Flow 1: First report from required data only

Renamed in content for this product: **the happy path.** Person types a question that maps cleanly to one governed metric ("What was total net revenue last week?"). Product responds: staged loading text, then an `answered` Outcome Card with metric, value, resolved time range ("last week" resolved against today's real date per TR6), and the `mf query` trace available on demand. The question and its `answered` outcome append to session history. Total elapsed time target: under 30 seconds (TR11).

### Flow 2: Future context-enriched gap-to-target review

Renamed in content for this product: **unknown metric.** Person asks about something with no governed metric behind it ("What's our churn rate?" when no churn metric exists). Product responds: an `unknown_metric` Outcome Card stating plainly that no governed metric matches, without guessing or approximating (FR3). The card includes a link/prompt to the Metrics Dictionary tab. Most likely wrong turn: the person assumes the tool is broken rather than understanding it's being deliberately honest — the copy must proactively rule that reading out ("This isn't a metric this tool tracks yet" reads very differently from "Error: no match found").

### Flow 3: Narrative refinement for audience fit

Renamed in content for this product: **ambiguous question.** Person asks something whose vocabulary plausibly maps to more than one governed metric with no disambiguating context ("How many requests did we get?" — API requests vs. quota-limit requests). Product responds: a distinct `ambiguous` Outcome Card (FR4) that names the ambiguity is the reason, not a missing metric, and does not guess. Most likely wrong turn: the person re-asks the exact same ambiguous phrasing expecting a different result — the card should nudge toward adding a qualifying word ("try 'API requests' or 'quota requests'") without pretending to know which the person meant.

### Flow 4: Future optional-source degradation

Renamed in content for this product: **unsupported domain.** Person asks a customer-service question ("Why did this customer file a ticket?"). Product responds: a distinct `unsupported_domain` Outcome Card (FR5), visually and verbally different from `unknown_metric` — this is a scoping boundary, not a data gap, and the copy should say so ("Customer-service questions aren't supported yet" rather than implying the metric merely doesn't exist). Most likely wrong turn: the person assumes this domain will eventually work the same way revenue/usage/quota do and keeps trying variants — one clear statement of current domain coverage (matching the header badges) should end that loop in one try.

### Flow 5: Required-data failure

Retained close to its original intent for this product: **system error.** The LLM backend is unreachable, returns malformed output, `mf` isn't found, MetricFlow query fails, or the query exceeds its timeout (TRD Failure Modes table, `doc/11.TRD_DETAILED.md`). Product responds: a `system_error` Outcome Card — the only outcome state allowed alert styling — with a retry action and language that places no blame on the person or their question ("Something went wrong running this — try again" rather than exposing the underlying exception). This state must never be counted toward the product's rejection-accuracy or false-rejection metrics (TR12); it is an infrastructure signal, not a product judgment about the question.

### Flow 6: Discovering what's askable (new for this product)

Person opens the app for the first time, or has just received a rejection, and doesn't know what's supported. They tap the Metrics Dictionary or Instructions tab before (or instead of) asking anything. Product responds by showing the governed metric list or the usage guide, with no API round-trip needed for Instructions and a fast `/catalog`-backed read for the Dictionary. They return to the Ask tab with a better-formed question. This flow exists specifically to reduce the frequency of Flows 2-4 over a session — discoverability is the mitigation for ambiguity, not a disambiguation dialogue (which is explicitly out of v1 scope).

## UI Components

### Claim-Labeled Narrative Block

Renamed for this product: **Outcome Card.** The single most important component in this UID.

- **Purpose:** render exactly one of the five backend `category` values as a visually and verbally distinct, first-class state — never a generic "result box" that happens to sometimes contain bad news.
- **States:** `answered`, `unknown_metric`, `ambiguous`, `unsupported_domain`, `system_error`, plus the screen-level empty and loading states it sits inside (documented under Key Screens, not duplicated here).
- **Rule it must always honor:** the Outcome Card's visual treatment (color, icon, heading) is driven exclusively by the `category` field from the response, never inferred from message text; `answered` never renders without the governing metric name and query trace; `unknown_metric`, `ambiguous`, and `unsupported_domain` never use alert/error styling (they are the product working as designed, not a failure); only `system_error` may use alert styling, and it must always pair with a retry action.

### Conversational Panel

Renamed for this product: **Question Input Bar.**

- **Purpose:** accept exactly one natural-language question at a time and submit it.
- **States:** idle/ready, submitting (Send disabled, text field still editable), disabled-pending-configuration (if no LLM provider is configured yet — matches the existing settings-modal-first pattern).
- **Rule it must always honor:** the input bar never carries or displays conversational context from a prior question — each submission is an independent request per TR1 and the PRD's exclusion of multi-turn disambiguation dialogue. It must not visually resemble a threaded chat transcript with memory it doesn't have (see Cross-Cutting Implementation Notes for the specific behavior in the existing frontend that violates this today).

### Combined Metrics Table

Renamed for this product: **Answer Detail Table.**

- **Purpose:** show the dimension breakdown inside an `answered` Outcome Card when the question requested one (e.g., "by model type").
- **States:** single-value (no table, just the value — most common case for a plain metric question), breakdown table (a handful of rows, one per dimension value), and a bounded/truncated state if MetricFlow returns more rows than reasonably fit (with a plain count of how many rows are hidden, never a silent truncation).
- **Rule it must always honor:** every column and value shown must trace to a `valid_dimensions` entry from the governing metric's catalog entry (TR7) — never a dimension invented or assumed by the UI layer.

### Trend Chart

Renamed for this product: **Tab Bar.**

- **Purpose:** persistent navigation between Ask, Metrics Dictionary, and Instructions.
- **States:** three mutually-exclusive selected states; no badges or unread indicators (nothing in this product needs them).
- **Rule it must always honor:** switching tabs never discards the Ask tab's in-progress question or session history — state persists across tab switches for the life of the page session.

### Dimension Segmentation Chart

Renamed for this product: **Session History List.**

- **Purpose:** show a lightweight, scannable record of this session's past questions and their outcome category, so a person doesn't lose track of what they already asked.
- **States:** empty (before any question), populated (append-only list, newest last or newest first — pick one and hold it consistently), no separate loading/error state (it only ever reflects completed Outcome Card results, never an in-flight one).
- **Rule it must always honor:** each entry shows the question text and its outcome category label — it must never show a truncated or reworded version of the answer that could be mistaken for a live result; it is a log entry, not a second live surface.

### Top Movers & Declines Table

Renamed for this product: **Metrics Dictionary List.**

- **Purpose:** the governed-metric browsing surface inside the Metrics Dictionary tab.
- **States:** loading (brief skeleton while `/catalog` resolves), populated (grouped by domain), error (catalog failed to load — see Key Screens).
- **Rule it must always honor:** content is sourced only from the `/catalog` endpoint's live data — this component must never hardcode a metric list that could drift from the actual semantic manifest (which is exactly the staleness risk the TRD's Integrations section already flags for the catalog cache itself).

### Supporting Signal Card

Renamed for this product: **Instructions Panel.**

- **Purpose:** the static usage-guide content inside the Instructions tab.
- **States:** none — this is static content bundled with the frontend, always fully present.
- **Rule it must always honor:** every example question shown must be one that would actually resolve to a supported governed metric today (verified against the catalog at the time this content is written) — a documentation surface that shows an example the product can't actually answer would itself become a source of the exact mistrust this product exists to remove.

### Version History Timeline

Renamed for this product: **Provider/Model Configuration Modal.**

- **Purpose:** the existing settings surface (already built) where a person selects an LLM provider, base URL, model, and API key (BYOK, FR8). Retained largely as-is from the current implementation.
- **States:** first-run (no settings saved, Cancel hidden, "Save & Start"), returning (settings saved, key pre-filled masked, "Continue"), editing.
- **Rule it must always honor:** an API key, once saved, is never redisplayed in plain text in the UI (the existing masked-value pattern is correct and must be preserved) and is never written to any client-visible log or console output — this mirrors the TRD's server-side requirement that the audit log excludes credentials (TR9 Security and Compliance) and extends the same discipline to the client.

### Operator Run-Status Components (operator surface only)

Not applicable to v1 — see Key Screens → Operator / Run-Status Surfaces for the reasoning. No components are specified here; this slot is retained to make the absence a documented decision rather than a silent gap, in case a future hosted/multi-user release reopens it.

## Wireframe Notes

### Report Screen (primary)

Referred to below as the **Ask Screen** (see Key Screens for why).

- **Above the fold, top to bottom:** header (product name + domain badges + provider/model badge) → tab bar (Ask / Metrics Dictionary / Instructions) → question input bar, full-width, always visible → Outcome Card region (empty, loading, or one of five outcomes), which is the visual center of gravity of the screen and should occupy the largest single block of vertical space once populated.
- **Below the fold:** session history list, oldest-to-newest or newest-first (consistent), scrollable independently of the page if it grows long.
- **Hierarchy:** the question input bar and the Outcome Card lead; the header and tab bar recede (smaller type, muted color, fixed height) so they never compete with the content the person came for, consistent with the deference tenet. The domain badges in the header are the one piece of header content that earns visual weight, because they set expectations before the person even types.
- **Primary action reachability:** the question input bar is reachable and focused with zero clicks on load (after any first-run provider configuration) and remains reachable with zero clicks after every outcome — the person should never have to scroll or click back to a fixed input location to ask their next question.

### Metrics Dictionary Tab (new)

- **Above the fold:** a short one-line purpose statement ("What this tool can answer") followed immediately by the first domain group (Revenue), so a person sees real content before any scrolling.
- **Layout:** grouped by domain in the same order as the header badges (Revenue, Token Usage, Quota); within each domain, metrics listed with name, one-line description, and a small tag for valid dimensions; a separate "Dimensions" section below the domain groups for the shared dimension glossary.
- **Hierarchy:** metric name leads (bold, larger), description defers (regular weight, muted color) — this is a reference surface, so scannability outranks visual richness.

### Instructions Tab (new)

- **Above the fold:** 3-5 example questions (one per built domain plus one showing a dimension breakdown), shown as plain text, not interactive.
- **Layout, in order:** example questions → how time phrases resolve (one short paragraph, referencing that they resolve against today's real date) → what each of the five outcomes means (one line each, in the same order and using the same labels/icons as the live Outcome Card, so the person recognizes them later) → what's explicitly out of scope (customer-service, multi-step "why" questions).
- **Hierarchy:** example questions lead, since they are the fastest path back to a successful Ask; the outcome-meaning list is second-most prominent because it directly serves the PRD's "tell me clearly when it cannot answer" user story.

### Operator Surfaces

Not applicable to v1 — no wireframe is specified. See Key Screens → Operator / Run-Status Surfaces.

# Cross-cutting implementation notes (for the engineer)

- **Drive rendering off `category`, not booleans.** The current `success`/`rejection` pair cannot express four of the five required outcomes. Do not build an interim UI that string-matches `rejection_reason` text to guess which of the four rejection categories applies — wait for the backend's TR12 `category` field, or coordinate with the Software Architect on a temporary explicit contract if the UI must ship before TR12 lands.
- **Remove context-threading language from the chat.** `sendChat()`'s `"Use the metrics from the last context"` suffix and the chat-bubble visual style both imply a multi-turn, context-aware conversation that v1 does not have and the PRD explicitly excludes (no disambiguation dialogue, no agent loop). Build the Question Input Bar and Session History List per this UID instead.
- **Remove narrative-synthesis content from the answer state.** The current `renderReport()`'s claim-tag prose ("Confirmed revenue driver," "Interpretation," "No operational context was connected...") oversells beyond FR1/TR1's literal single-metric-value contract and directly conflicts with the PRD's Non-Goals. The `answered` Outcome Card states the metric, value, time range, and dimensions — nothing synthesized.
- **Metrics Dictionary tab needs no new backend endpoint.** `GET /catalog` already returns the exact shape this tab needs (`domains`, `metrics[]`, `dimensions[]`) — confirmed by reading `catalog_builder.py`. This is a frontend-only build.
- **Accessibility is part of the five-state design, not an add-on.** Each outcome state must be distinguishable by icon and label text alone, not color alone, for contrast/color-blindness reasons. The tab bar and settings modal must be fully keyboard-navigable. Given waits of up to 30 seconds, the loading state's staged status text should be exposed via an `aria-live="polite"` region so assistive technology announces progress rather than leaving a screen-reader user in silence.
- **Credential hygiene extends to the client.** Never log or console-print the `api_key` field, in any code path, including error/catch blocks — this mirrors TR9's server-side exclusion requirement.
