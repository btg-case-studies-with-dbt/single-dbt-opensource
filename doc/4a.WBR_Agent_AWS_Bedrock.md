# Technical Requirements Document
## TRD-04: WBR Conversational Agent — AWS Bedrock Edition
**Version:** 1.0 | **Status:** Draft | **Prerequisite:** TRD-01 local version working

---

## 1. Purpose

Deploy the WBR Conversational Agent built in TRD-01 to AWS using managed services.
The agent logic (LangChain, tools, RAG pipeline) stays identical. Only the
infrastructure underneath changes — local Docker/Ollama/pgvector is replaced by
Bedrock/RDS/S3/App Runner.

This document is written for Claude Code to implement end to end using AWS CLI only.
No AWS Console steps. No IaC (CDK/Terraform). Pure CLI commands.

---

## 2. Architecture

```
User (Browser)
    ↓ HTTPS
CloudFront
    ↓
S3 (React static site)
    ↓ API calls
App Runner (FastAPI container)
    ├── LangChain ReAct Agent
    │   ├── revenue_tool     → RDS PostgreSQL (revenue data)
    │   └── search_tickets   → Bedrock Knowledge Base (tickets + WBR docs)
    └── Bedrock
            ├── Meta Llama 3.3 70B Instruct  (reasoning)
            └── Titan Embed Text v2           (embeddings, managed by KB)

Data layer:
    S3 bucket
        ├── customer_tickets.csv   → Bedrock Knowledge Base syncs automatically
        ├── wbr_docs/*.docx        → Bedrock Knowledge Base syncs automatically
        └── revenue/
            └── wbr_revenue.csv    → loaded into RDS at setup time

RDS PostgreSQL 16
    ├── pgvector extension
    └── wbr_revenue table (structured data, queried by revenue_tool)
```

## 3. Local vs AWS Component Mapping

| Local (TRD-01) | AWS (TRD-04) | Notes | Bedrock component |
|---|---|---|---|
| Ollama llama3.1:8b | Bedrock Meta Llama 3.3 70B Instruct | Same model, managed inference | Bedrock LLM |
| Ollama nomic-embed-text | Bedrock Titan Embed Text v2 | Managed by Knowledge Base | Knowledge Base (embeddings) |
| pgvector Docker | RDS PostgreSQL 16 + pgvector | Managed DB | RDS (data layer) |

| FastAPI uvicorn local | App Runner containerized FastAPI | Managed container | App Runner |
| React Vite local | S3 + CloudFront | Static hosting | S3 + CloudFront |
| backend/.env | AWS Systems Manager Parameter Store | Secrets management | — |
| LangChain code | Same LangChain code on App Runner | No code changes | Agent / Orchestration |
| NeMo Guardrails | Bedrock Guardrails API (or second LLM call for adversarial review) | Guardrails shift to managed service or prompt-layer enforcement | Guardrails |

| Semantic layer (dbt YAML) | S3-hosted metric definitions loaded at startup per §16.2 | Prompt Engineering + Knowledge Base |

## 6. Step 2 — RDS PostgreSQL Setup

### 6.1 Create VPC and subnet group (required for RDS)
```bash
# Get default VPC
VPC_ID=$(aws ec2 describe-vpcs \
  --filters "Name=is-default,Values=true" \
  --query "Vpcs[0].VpcId" --output text)

# Get subnets
SUBNET_IDS=$(aws ec2 describe-subnets \
  --filters "Name=vpc-id,Values=${VPC_ID}" \
  --query "Subnets[*].SubnetId" --output text | tr '\t' ',')

# Create DB subnet group
aws rds create-db-subnet-group \
  --db-subnet-group-name ${PROJECT}-subnet-group \
  --db-subnet-group-description "WBR Agent subnet group" \
  --subnet-ids $(echo $SUBNET_IDS | tr ',' ' ')
```

### 6.2 Create security group
```bash
SG_ID=$(aws ec2 create-security-group \
  --group-name ${PROJECT}-rds-sg \

  --query GroupId --output text)

# Allow PostgreSQL from anywhere (restrict to App Runner CIDR in production)
aws ec2 authorize-security-group-ingress \
  --group-id ${SG_ID} \
  --protocol tcp \
  --port 5432 \
  --cidr 0.0.0.0/0
```

### 6.3 Create RDS instance

## 7. Step 3 — Bedrock Knowledge Base Setup

The Knowledge Base replaces both `ingest.py` and `ingest_wbr.py`.
Bedrock reads from S3, embeds using Titan Embed Text v2, and stores in a
managed vector store. Chunking strategy: hierarchical (Bedrock default for docx).

### 7.1 Create IAM role for Knowledge Base
```bash
# Create trust policy
cat > /tmp/kb-trust-policy.json << 'JSON'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "bedrock.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
JSON

KB_ROLE_ARN=$(aws iam create-role \
  --role-name ${PROJECT}-kb-role \
  --assume-role-policy-document file:///tmp/kb-trust-policy.json \
  --query Role.Arn --output text)

# Attach S3 and Bedrock permissions
aws iam attach-role-policy \
  --role-name ${PROJECT}-kb-role \
  --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

aws iam attach-role-policy \
  --role-name ${PROJECT}-kb-role \
  --policy-arn arn:aws:iam::aws:policy/AmazonBedrockFullAccess
```

### 7.2 Create Knowledge Base
```bash
KB_ID=$(aws bedrock-agent create-knowledge-base \
  --name ${PROJECT}-knowledge-base \
  --role-arn ${KB_ROLE_ARN} \
  --knowledge-base-configuration '{
    "type": "VECTOR",
    "vectorKnowledgeBaseConfiguration": {
      "embeddingModelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0"
    }
  }' \
  --storage-configuration '{
    "type": "RDS",
    "rdsConfiguration": {
      "resourceArn": "arn:aws:rds:us-east-1:'${AWS_ACCOUNT_ID}':db:'${PROJECT}'-postgres",
      "credentialsSecretArn": "'${SECRET_ARN}'",
      "databaseName": "wbr_vectors",
      "tableName": "bedrock_kb_embeddings",
      "fieldMapping": {
        "primaryKeyField": "id",
        "vectorField": "embedding",
        "textField": "chunks",
        "metadataField": "metadata"
      }
    }
  }' \
  --query knowledgeBase.knowledgeBaseId --output text)

echo "Knowledge Base ID: ${KB_ID}"
```

### 7.3 Create data source pointing to S3
```bash
DS_ID=$(aws bedrock-agent create-data-source \
  --knowledge-base-id ${KB_ID} \
  --name ${PROJECT}-s3-source \
  --data-source-configuration '{
    "type": "S3",
    "s3Configuration": {
      "bucketArn": "arn:aws:s3:::wbr-agent-data-'${AWS_ACCOUNT_ID}'",
      "inclusionPrefixes": ["knowledge-base/"]
    }
  }' \
  --vector-ingestion-configuration '{
    "chunkingConfiguration": {
      "chunkingStrategy": "HIERARCHICAL",
      "hierarchicalChunkingConfiguration": {
        "levelConfigurations": [
          {"maxTokens": 1500},
          {"maxTokens": 300}
        ],
        "overlapTokens": 60
      }
    }
  }' \
  --query dataSource.dataSourceId --output text)

echo "Data Source ID: ${DS_ID}"
```

### 7.4 Start ingestion job
```bash
aws bedrock-agent start-ingestion-job \
  --knowledge-base-id ${KB_ID} \
  --data-source-id ${DS_ID}

# Wait for completion (check status)
aws bedrock-agent get-ingestion-job \
  --knowledge-base-id ${KB_ID} \
  --data-source-id ${DS_ID} \
  --ingestion-job-id $(aws bedrock-agent list-ingestion-jobs \
    --knowledge-base-id ${KB_ID} \
    --data-source-id ${DS_ID} \
    --query "ingestionJobSummaries[0].ingestionJobId" --output text) \
  --query "ingestionJob.status" --output text
# Expected: COMPLETE
```

### 7.5 Weekly sync (when new WBR document is added)
```bash
# Drop new docx into S3
aws s3 cp data/wbr_docs/wbr_week_53.docx \
  s3://${PROJECT}-data-${AWS_ACCOUNT_ID}/knowledge-base/wbr-docs/

# Trigger re-sync
aws bedrock-agent start-ingestion-job \
  --knowledge-base-id ${KB_ID} \
  --data-source-id ${DS_ID}
```

### 8.2 Changes to ticket_tool.py and wbr_doc_tool.py

Replace pgvector local search with Bedrock Knowledge Base retrieval:

```python
# Remove: PGVector vectorstore search
# Add: Bedrock Knowledge Base retrieval

import boto3

bedrock_agent_runtime = boto3.client(
    "bedrock-agent-runtime",
    region_name=os.getenv("AWS_REGION", "us-east-1")
)

def search_knowledge_base(query: str, kb_id: str, n_results: int = 5) -> list:
    response = bedrock_agent_runtime.retrieve(
        knowledgeBaseId=kb_id,
        retrievalQuery={"text": query},
        retrievalConfiguration={
            "vectorSearchConfiguration": {"numberOfResults": n_results}
        }
    )
    return response["retrievalResults"]
```

|---|---|---|
| LLM | Groq API | Bedrock managed |
| Embeddings | Ollama local | Titan Embed v2 managed |

## 15. Interview Talking Points

- Bedrock Knowledge Base uses the same pgvector technology as the local version —
  same architecture, managed by AWS
- Titan Embed Text v2 replaces nomic-embed-text — same role, production-grade
- App Runner was chosen over Lambda because the agent reasoning takes 10-30 seconds
  — Lambda's cold start + execution model is not suited for long-running LLM calls
- The agent LangChain code is identical between local and AWS — only the LLM and
  retrieval backends change, demonstrating clean separation of concerns
- Weekly WBR document ingestion reduces from a manual Python script to a single
  S3 upload + CLI sync trigger — operational burden drops significantly

### 16.1 Skills Layer on Bedrock

In the local version, skills are markdown files read by the agent from disk.
In Bedrock, skills are stored in S3 and loaded via the Knowledge Base or passed
as system prompt context.

**Bedrock skills architecture:**

```
S3 bucket: wbr-agent-data-{account_id}/
├── knowledge-base/          ← tickets and WBR docs (ingested by KB)
│   ├── tickets/
│   └── wbr-docs/
└── skills/                  ← NEW: skill files loaded at agent startup
    ├── wbr_knowledge.md     ← domain router
    ├── wbr_unbook.md        ← procedural workflow
    └── wbr_business_context.md  ← business definitions
```

Skills are NOT ingested into the Knowledge Base. They are read directly by the
agent at startup via a `read_skill` tool that fetches from S3.

```python
def read_skill(skill_name: str) -> str:
    s3 = boto3.client("s3")
    obj = s3.get_object(
        Bucket=f"wbr-agent-data-{account_id}",
        Key=f"skills/{skill_name}.md"
    )
    return obj["Body"].read().decode("utf-8")
```

### 16.2 Semantic Layer — Bedrock Implementation

The semantic layer in the local version is defined in dbt schema YAML.
In Bedrock, it is passed as structured context in the agent system prompt,
loaded from a governed metric definitions file in S3.

```
S3: skills/metric_definitions.json
{
  "net_revenue": {
    "formula": "arr + new_bookings - churn",
    "grain": "weekly, by region and segment",
    "owner": "Finance"
  },
  "churn_rate": {
    "formula": "churn / arr",
    "type": "gross churn",
    "owner": "Finance"
  }
}
```

The agent reads this at startup and is instructed to check it before
writing any query or calling any tool.

### 16.3 Adversarial Review Sub-Agent on Bedrock

Implement adversarial review as a second Bedrock agent invocation.

```python
def adversarial_review(answer: str, tool_outputs: str) -> dict:
    bedrock_runtime = boto3.client("bedrock-runtime", region_name="us-east-2")
    response = bedrock_runtime.converse(
        modelId="meta.llama3-3-70b-instruct-v1:0",
        messages=[{
            "role": "user",
            "content": [{"text": ADVERSARIAL_PROMPT.format(
                answer=answer,
                tool_outputs=tool_outputs
            )}]
        }]
    )
    result = response["output"]["message"]["content"][0]["text"]
    return {"passed": result.startswith("PASS"), "feedback": result}
```

Only return to the user if adversarial review passes.

### 16.4 Offline Eval Framework on Bedrock

Store eval results in RDS for trend analysis:

```sql
CREATE TABLE agent_evals (
    eval_id      TEXT PRIMARY KEY,
    question     TEXT,
    expected     TEXT,
    actual       TEXT,
    passed       BOOLEAN,
    model_id     TEXT,
    skill_version TEXT,
    run_at       TIMESTAMPTZ DEFAULT NOW()
);
```

Run evals on every deployment via a Lambda function triggered by ECR push.
Gate App Runner deployment: do not deploy if pass rate drops below 85%.

### 16.5 Provenance Footer — Bedrock Implementation

Every response from the Bedrock agent must include:

```
Source: semantic layer | Bedrock KB (tickets) | Bedrock KB (WBR docs) | RDS revenue table
Freshness: week_ending 2024-08-11
KB sync: last synced 2024-08-12T06:00:00Z
Confidence: High
Reviewed: adversarial review ✓
```

Add this as a required output format in the Bedrock agent instruction.

### 16.6 Skill Maintenance — AWS Automation

When a new WBR document is added to S3, automatically check if skill files
need updating via a Lambda trigger:

```
S3 event: new file in knowledge-base/wbr-docs/
    → Lambda: check skills/wbr_knowledge.md for staleness
    → If last modified > 30 days ago, send SNS alert to data team
    → "Skill file may be stale — review wbr_knowledge.md"
```

This is the AWS equivalent of Anthropic's CI hook that flags model changes
without corresponding skill updates.

### 16.7 Key Lessons Applied

| Anthropic Finding | Applied to WBR Agent AWS |
|---|---|
| Without skills, accuracy < 21% | Skills layer added to both local and Bedrock versions |
| Semantic layer must be mandatory first step | Metric definitions loaded at startup, checked before any tool call |
| Adversarial review adds 6% accuracy | Second Bedrock invocation added for review before response |
| Skill docs go stale in weeks | S3 skill files colocated with dbt models, Lambda staleness alert |
| Query corpus RAG adds < 1% accuracy | WBR docs and tickets use hierarchical chunking, not raw query history |
| Provenance footer builds trust | Added to every agent response |
| Offline evals essential | Eval suite in RDS, gating App Runner deployment |
