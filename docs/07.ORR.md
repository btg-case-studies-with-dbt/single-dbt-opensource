## 0. What "running" means here

Two independently-startable pieces. **Neither starts the other.**

| Piece | Started by | Contains |
|---|---|---|
| Data/infra plane | `docker compose up -d` | Postgres, Airflow, Metabase, pgAdmin |
| Query backend (the app) | **hand-started** (see below) | FastAPI `/query`, catalog, MetricFlow CLI, LLM client, static SPA |

**The `/query` backend is NOT a compose service.** `docker compose up -d` will happily
report success while the API is down. This is the single most common "why is it not
working" trap — the operator assumes compose started everything.

**Canonical boot recipe** (from `conversational-bi/`):

```bash
docker compose up -d                       # data/infra plane (Postgres et al.)
cd conversational-bi
DBT_HOST=localhost .venv/bin/python -m uvicorn backend.main:app --port 8000
```

**Non-negotiable boot preconditions** (each is a real failure mode if missed — see §2):

1. **`DBT_HOST=localhost` is REQUIRED on the host.** MetricFlow reaches the prod marts on
   `localhost`; the in-container default is `postgres`, which does not resolve from the host.
   Without it, `/query` executes but MetricFlow cannot connect.
2. **Use the pinned venv (`.venv`, Python 3.11 + `requirements.txt`).** System Python 3.9
   and Homebrew 3.14 lack the pinned stack (Presidio/spaCy `en_core_web_lg` is a hard import
   dependency; the OTLP exporter imports unconditionally). `.venv/bin/python`, not `python`.
3. **A configured LLM provider** via gitignored `conversational-bi/.env` (see §4).

**Eval / data window:** the marts hold `2025-10-20 .. 2026-01-19`. Questions resolved
outside this window return zero rows *correctly* (not an error). The window is pinnable per
request via the `time_override` field on `POST /query` — this is the intended interface for
reproducible evaluation, not a bug workaround.

## 1. Health & observability

### Health check — the one signal

```bash
curl -s http://localhost:8000/health
```

**Healthy** means all four fields are truthy:

```json
{"status":"healthy","catalog_loaded":true,"catalog_metrics_count":44,"mf_cli_available":true}
```

| Field | Healthy value | Unhealthy means |
|---|---|---|
| `status` | `healthy` | process/app-level fault |
| `catalog_loaded` | `true` | catalog failed to load → every query is `unknown_metric` (§2) |
| `catalog_metrics_count` | `44` (current served catalog) | `0` → empty catalog (§2) |
| `mf_cli_available` | `true` | `mf` not on PATH / wrong venv → every query `system_error` (§2) |

Supporting endpoints: `/` → **307** redirect to `/frontend/` (the static SPA); `/info`
(service metadata + endpoint map); `/catalog` (the metric list, no LLM call — a cheap way to
prove the catalog is loaded without spending a provider token); `/docs` (OpenAPI).

**Verified live this session (2026-07-11):**
- `/health` → `{"status":"healthy","catalog_loaded":true,"catalog_metrics_count":44,"mf_cli_available":true}` — **PASS**
- `/` → `HTTP/1.1 307 Temporary Redirect`, `location: /frontend/` — **PASS**
- `/catalog` → returns 44 metrics across domains Quota / Revenue / Token usage — **PASS**

### Logs — where they go

- **Uvicorn/application log:** stdout of the hand-started uvicorn process (INFO level via
  `logging.basicConfig`). This is the operator's live tail. No log file is written by
  default; if you want persistence, redirect stdout (`... uvicorn ... 2>&1 | tee run.log`).
- **Structured audit log (FR9):** JSON Lines appended to
  `conversational-bi/evidence/query_log.jsonl`, one record per `/query`.

### FR9 structured logging is credential-free — VERIFIED

Each audit record (built in `backend/main.py`, `_write_audit_log`) contains **exactly**:

```
timestamp · elapsed_seconds · question · category · metric · dimensions · time_range · domain
```

- **No API key, no Authorization header, no raw request object is serialized.** The record is
  a hand-built dict of routing fields, not the request.
- **`question` is PII-redacted** before it is written: the field is
  `_pii_redactor.redact(question)` (Presidio-backed), not the raw input.
- **Verification performed this session:** `grep -icE "sk-|api_key|authorization|bearer|OPENAI_API_KEY"`
  over the entire `evidence/query_log.jsonl` → **0 matches**. Sampled record key set matches
  the list above exactly. — **PASS**

**Optional tracing:** OpenTelemetry is off by default; `OTEL_ENABLED=true` turns on span
export. Not required for the local slice; a `_NoopTracer` stands in when disabled.

## 2. Runbook — named failure modes (symptom → cause → recovery)

Each of these is a *real* trap in this system, not a generic one. Detection everywhere is
the `/health` check plus the uvicorn stdout tail.

### 2.1 Backend won't boot
- **Symptom:** `curl /health` connection-refused; uvicorn exits on start; `ModuleNotFoundError`,
  spaCy/`en_core_web_lg` load error, or OTLP import error in the traceback.
- **Cause:** wrong interpreter (system 3.9 / Homebrew 3.14 instead of the pinned 3.11 venv), or
  the venv was never built / is stale against `requirements.txt`.
- **Recovery:**
  1. Confirm you are invoking `conversational-bi/.venv/bin/python` (not bare `python`).
  2. If the venv is missing/stale: `cd conversational-bi && python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt`.
  3. Re-run the boot recipe (§0). Confirm `/health` is healthy.

### 2.2 `/query` returns 500 / `system_error`
- **Symptom:** `POST /query` responds with `category: system_error`, or HTTP 500; uvicorn log
  shows a MetricFlow/`mf` connection or subprocess error.
- **Cause (most common):** `DBT_HOST` unset or wrong — MetricFlow tries the in-container default
  `postgres` host, which does not resolve from the host machine. Secondary: `mf` not on PATH
  (wrong venv), or Postgres container down.
- **Recovery:**
  1. Confirm the process was started with `DBT_HOST=localhost` (re-export and restart uvicorn).
  2. `/health` → check `mf_cli_available:true`. If false, you are in the wrong venv (see §2.1).
  3. Confirm the data plane is up: `docker compose ps` shows Postgres running.
  4. `system_error` is the *correct, designed* response for infra failure — it is loud and
     traceable, not a silent wrong answer. The fix is the environment, not the code.

### 2.3 Empty results (out-of-window time)
- **Symptom:** query returns `category: answered` with **0 rows** and looks "broken."
- **Cause:** the question's time window falls outside the marts' data window
  `2025-10-20 .. 2026-01-19`. This is **not** a fault — zero rows for a valid, unmatched window
  is correct behavior.
- **Recovery:**
  1. Reproduce with an in-window date by passing `"time_override":"2026-01-15"` (any date inside
     the window) on `POST /query`.
  2. If rows now appear, the empty result was expected. No code change.
  3. This is the intended eval interface — use `time_override` to pin reproducible windows.

### 2.4 Catalog empty
- **Symptom:** `/health` shows `catalog_loaded:false` or `catalog_metrics_count:0`; every
  question routes to `unknown_metric`.
- **Cause:** the semantic catalog artifacts weren't produced/loaded (e.g. `dbt parse` /
  manifest not generated, or the catalog file is missing at startup).
- **Recovery:**
  1. Rebuild the catalog inputs: from `dbt/`, with `DBT_HOST=localhost`, run `dbt parse`
     (regenerates `manifest.json` / `semantic_manifest.json` the catalog builder reads).
  2. Restart uvicorn (catalog loads at startup).
  3. Confirm `/catalog` returns metrics and `/health` shows `catalog_metrics_count:44`.

### 2.5 Provider / key failure
- **Symptom:** `/query` returns `system_error` referencing the LLM call; uvicorn log shows a
  401/403/timeout from the provider; `catalog`/`health` are fine (proves it's the provider,
  not the app).
- **Cause:** missing/invalid/**rotated-away** key, wrong `OPENAI_BASE_URL`/`OPENAI_MODEL`, or
  the provider is unreachable. Current provider: opencode/deepseek-v4-pro via the
  OpenAI-compatible path, configured in gitignored `conversational-bi/.env`.
- **Recovery:**
  1. Isolate: `/health` healthy + `/catalog` OK + only `/query` failing on the LLM step → it's
     the provider, not the app.
  2. Fix `.env` (`OPENAI_BASE_URL`, `OPENAI_MODEL`, `OPENAI_API_KEY`). Restart uvicorn (`.env`
     is read at boot).
  3. **Fallback:** switch to local ollama (`LLM_PROVIDER=ollama`, pull the model) — no key
     required. `.env` is the single swap point; see `.env.example`.
  4. See §4 — the current opencode key is **exposed and must be rotated**.

### 2.6 dbt build red
- **Symptom:** `dbt build --target prod` exits non-zero; a model/contract or RI test fails.
- **Cause:** environment (`DBT_HOST` unset, Postgres down) or a real model/test regression.
- **Recovery:**
  1. Run from `dbt/` with `DBT_HOST=localhost`: `dbt build --target prod`. **Green = exit 0**
     with all tests passing (this session's clean run is the reference; the pass *count* has
     moved as the model set changed — 484 at DECISION_LOG #12, ~519 this session — so gate on
     **exit 0 / 0 failures**, not a fixed number).
  2. Referential integrity is enforced by **dbt `relationships`/`not_null`/`unique` tests, not
     DB constraints** (DECISION_LOG #12). A red RI test means a real bad-row/lineage problem —
     read the failing test, do not "fix" it by adding a DB constraint.
  3. If the failure is a recent change, see §3 (rollback).

### Git operational note (not a service failure, but a real trap)
Device-bridge git can leave a stale `.git/*.lock`. **Run git from the Mac terminal.** If you
hit "index.lock exists," remove the stale lock only after confirming no git process is
running: `rm -f .git/index.lock`.

## 3. Rollback — return to last-known-good

Rollback here is `git revert` + rebuild the affected plane. There is no deployment automation
(none is in scope for a local case study); the mechanism is git plus a restart.

### Last-known-good commit lineage (current stable state)
```
9f869f4  Step 3 / M3 CLOSED: root '/' -> /frontend/ 307 redirect; UI parity verified   <- current tip of stable
99188b9  Step 2/2b: int_revenue_daily yml fix -> clean 'dbt build --target prod'
e39e3fe  Step 2/2a: dbt RI fix (remove broken PK/FK post_hooks); RI via dbt tests
bea7ce2  M1 CLOSED: accuracy 98.6% proven, MetricFlow-only (DECISION_LOG #11)
```

### The two "recent change" reverts are each effectively one line
- **Root redirect** (`9f869f4`): the `/` → `/frontend/` 307 lives in `backend/main.py` `root()`
  (`RedirectResponse(url="/frontend/", status_code=307)`). Revert = drop/replace that return.
  App-only change; restart uvicorn, no data touched.
- **dbt RI fix** (`e39e3fe`): removed PK/FK `post_hook`s from 3 dims + 3 facts. **Two-way door**
  (DECISION_LOG #12 records the reversal path: "restore post_hooks"). Revert the commit,
  re-run `dbt build --target prod`.

### Rollback procedure
1. Identify the bad commit; `git revert <sha>` (from the Mac terminal — §2 git note).
2. **App-plane change** (backend code, redirect, `.env`): restart uvicorn (§0). Confirm `/health`.
3. **Data-plane change** (dbt models/tests): re-run `dbt build --target prod` with
   `DBT_HOST=localhost`; confirm exit 0.
4. **Door class matters:** the redirect and the RI fix are two-way (cheap to reverse). A change
   to the **5-category response contract** or to a **metric definition** is a one-way door
   (DECISION_LOG #11) — do not revert those casually; route to the TPM.

## 6. Escalation / flag to the TPM (not SRE calls)

- **Key rotation (gate #13):** SRE flags it as a launch blocker; only the human can rotate the
  provider key and revoke the exposed one. **TPM decision to gate launch on it.**
- **One-way-door reverts:** any change to the 5-category response contract or a metric
  definition is a one-way door (DECISION_LOG #11/#12) — route to the TPM, do not roll back at
  the infra layer.
- **Scope beyond local single-user:** multi-user, HA, cloud infra, alarms/paging, and a real
  security boundary are explicitly out of this ORR's scope per the DECISION_LOG assumption. If
  the case study is ever promoted to a shared/deployed environment, that is a new architecture
  decision (deployment topology + scale envelope + security boundary) the TPM routes back
  before this ORR is extended.

## 7. Out of scope (clean seams, deliberately not built)

Multi-user concurrency and HA · cloud IaC / deploy pipeline · alarms and on-call paging ·
error-budget/SLO policy (single-operator: the SLI is "`/health` is healthy and `/query`
answers"; no formal budget) · capacity/scale plan beyond one machine · secret manager /
credential rotation automation (manual `.env` swap is enough for one operator). Each is a seam,
not a gap — named here so a future promotion knows exactly what it must add.
