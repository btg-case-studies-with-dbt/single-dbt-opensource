# Idea

**Product:** Governed Metric Execution Architecture for Agentic BI
**Document type:** One-pager
**Owner:** Kanja Saha
**Status:** Draft for review
**Date:** 2026-07-02

## Problem

Cross-functional teams at an AI-inference platform read revenue, token usage,
quota, and customer evidence through separate tools. A simple business question
can require dashboard checks, manual metric reconciliation, and ad hoc context
gathering from support tickets or feedback. The risk is not only slowness; it is
that an AI interface may answer from plausible language instead of governed
metrics.

## Customer

The first users are RevOps, finance, engineering capacity, and customer-facing
operators who need one trustworthy answer across revenue, usage, quota, and
later support evidence. They need natural-language access, but they cannot accept
raw SQL generation, invented metrics, or unsupported narrative claims.

## Proposed Solution

Build a local, inspectable agentic BI architecture on synthetic AI-inference
platform data. Quantitative answers execute only through the existing dbt and
MetricFlow semantic layer. The LLM selects from governed metrics and dimensions;
the backend validates that selection against the semantic manifest before
execution. RAG is reserved for qualitative customer evidence such as support
tickets and feedback, not for executing analytics.

The architecture demonstrates a clean trust boundary:

- dbt and MetricFlow own governed metric definitions and quantitative execution.
- The LLM routes, plans, and synthesizes, but never generates warehouse SQL.
- Customer evidence retrieval supplies cited context for investigation
  narratives after metric results are known.

## First Value

A user asks one supported business question, such as "What was total net revenue
last week?" or "Show total API requests by model type this quarter." The service
maps the question to an approved metric, validates the dimensions and time range,
runs `mf query`, and returns either one governed answer or a clear rejection
category.

## Why Now

Teams are adopting AI interfaces for analytics before their metric contracts and
evidence boundaries are ready. This project shows the safer pattern: let natural
language improve access, but keep the semantic layer as the source of truth. It
also sets up the next architecture layer, where customer support tickets and
feedback can explain metric movement without becoming a source of quantitative
truth.

## Non-Goals For V1

- No raw SQL generation by the LLM.
- No automatic metric creation.
- No customer-service metric answers until their semantic model and governed
  metrics exist.
- No multi-step root-cause agent loop in the first governed-query path.
- No production multi-tenant deployment.
- No real customer data.

## Expansion Direction

The architecture is designed to expand in three controlled steps:

1. **Governed metric routing:** one natural-language question maps to one
   approved MetricFlow query.
2. **Customer evidence RAG:** support tickets, feedback, notes, and issue records
   are indexed with metadata aligned to governed dimensions, then retrieved as
   cited qualitative context.
3. **Agentic investigations:** LangGraph coordinates multi-step metric queries,
   evidence retrieval, contradiction checks, and grounded synthesis while every
   quantitative value still comes from MetricFlow.

## Success Signal

The project is successful when a reviewer can trace a natural-language question
through metric selection, manifest validation, MetricFlow execution, and answer
rendering, and can see that future RAG over customer evidence adds cited context
without bypassing governed metrics.
