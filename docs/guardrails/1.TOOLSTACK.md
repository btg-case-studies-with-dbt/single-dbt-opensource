# aiTechne - Canonical Toolstack

**Status:** Project guardrail for the aiTechne governed-metrics test case. This file records the stack already used by this repository. Changes require human approval and an entry in `docs/8.DECISION_LOG.md`.

## Product Shape

An open-source data platform that loads source data into PostgreSQL, transforms and tests it with dbt Core, publishes governed metrics through MetricFlow, orchestrates recurring work with Airflow, and answers natural-language questions through a guarded FastAPI service.

## Languages And Configuration

- Python for orchestration, APIs, governed query routing, and tests.
- SQL and Jinja for dbt transformations, tests, snapshots, and governed marts.
- YAML for dbt resources, MetricFlow semantic models, Airflow and evaluation configuration.
- HTML, CSS, and JavaScript for the existing lightweight conversational BI frontend.

Do not add another primary language or frontend framework without explicit human approval.

## Database

- PostgreSQL 17 is the analytical database and MetricFlow query target.
- The local container image is `pgvector/pgvector:pg17`; pgvector is available for approved retrieval work.
- Database changes are expressed through governed dbt models, seeds, snapshots, tests, or an approved migration mechanism.
- Application-generated SQL must not bypass the governed semantic and contract boundaries.

## Transformation And Semantic Layer

- **dbt Core is explicitly approved and required.** It is the primary transformation and testing framework.
- `dbt-postgres` is the approved adapter for this repository.
- MetricFlow through `dbt-metricflow` is the governed metric execution layer.
- dbt semantic YAML, models, tests, seeds, snapshots, and generated artifacts must remain consistent with `docs/contracts/1.METRIC_DICTIONARY.csv`.
- Quantitative answers must come from governed MetricFlow/dbt execution. The LLM may select and explain metrics; it may not invent values or generate an ungoverned warehouse query path.

## Orchestration

- Apache Airflow 2.11.2 with `LocalExecutor` is the approved local orchestrator.
- Airflow owns scheduled pipeline execution and calls dbt through the repository's existing DAGs.
- Pipelines must be idempotent, observable, and safe to replay through the orchestrator.

## API And Conversational BI

- FastAPI with Uvicorn is the approved backend API stack.
- The current frontend is static HTML, CSS, and JavaScript served by the application.
- Metabase is the approved local BI inspection surface; pgAdmin is an operational database tool, not a reporting source of truth.
- API responses follow the governed response contract in the TRD and detailed design.

## LLM Providers

- The provider seam supports local Ollama and user-supplied OpenAI-compatible or Anthropic credentials.
- Provider selection is configuration-driven; provider-specific behavior stays behind the existing client boundary.
- LLMs perform routing and synthesis only. Metric names, dimensions, filters, and returned numbers are validated against the governed catalog.
- On ambiguity, missing governance, stale data, or provider failure, the system asks, abstains, or returns an explicit failure. It does not guess.

## Packaging And Local Runtime

- Docker Compose is the approved local environment for PostgreSQL, Airflow, Metabase, and pgAdmin.
- The repository Dockerfile is based on the pinned Airflow image and installs dbt into its isolated virtual environment.
- Local Python virtual environments are permitted for the conversational BI service and evaluation tooling.

## Testing And Quality Gates

- dbt tests and `dbt build` gate data-model changes.
- Python `unittest` suites gate backend and guardrail behavior.
- Promptfoo evaluations and the JavaScript assertion self-tests gate governed routing and never-fabricate behavior.
- GitHub Actions is the approved CI mechanism for existing dbt and conversational BI checks.
- Generated dbt artifacts such as `manifest.json`, `run_results.json`, and failure evidence may be consumed for diagnosis, but generated output is not hand-edited.

## Secrets And Data Safety

- Credentials and provider keys come from environment configuration and are never committed, logged, or embedded in frontend code.
- Synthetic data is the default test and demonstration input unless a separately approved data-handling contract permits otherwise.
- Source data and warehouse access remain read-only unless an approved contract explicitly says otherwise.

## Prohibited Without Approval

- Replacing dbt Core, MetricFlow, Airflow, PostgreSQL, or FastAPI with a parallel primary framework.
- Defining a metric independently in SQL, application code, prompts, or dashboards instead of the metric dictionary and semantic layer.
- Letting an LLM generate or execute arbitrary warehouse SQL.
- Adding a second orchestrator, semantic layer, database, API framework, or evaluation framework for the same responsibility.
- Silent fallbacks, fabricated values, hard-coded secrets, or unreviewed dependency additions.

**Rule for agents:** Use this stack as the default. dbt is allowed and central. Any exception must be approved by the human and recorded before implementation.
