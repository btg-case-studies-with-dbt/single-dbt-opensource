# Technical Requirements Document

**Product:** Governed Metric Execution Architecture for Agentic BI
**Status:** Draft for review
**Owner:** Solutions Architect
**Date:** 2026-07-02
**Source inputs:** Consolidated from the project technical notes into the canonical documentation chain.

## Scope

In scope: a local FastAPI service that accepts one natural-language question or one bounded clarification reply, uses an LLM to select from the governed MetricFlow catalog on the initial turn, validates the result against the semantic manifest, executes `mf query`, and returns one governed answer or one categorized non-answer.

Out of scope: raw SQL generation, automatic metric creation, production multi-tenant deployment, customer-service metrics before semantic modeling, and multi-step LangGraph investigations in v1.

Deployment model: local Docker Compose data stack plus FastAPI app, single-user or small sequential local use.

## Architecture Tenets

1. MetricFlow is the only path to quantitative data.
2. Rejection categories must be specific and machine-checkable.
3. Infrastructure failure is never a product rejection.
4. Server-side validation is the enforcement point; prompts are hints.
5. Provider selection is BYOK/config-driven.

## Functional Requirements

| ID | Requirement | Done When |
|---|---|---|
| TR1 | Accept one natural-language question or one clarification reply and return one governed result. | Response includes metric, value, time range, dimensions, and category; clarification replies carry client-provided continuation context. |
| TR2 | Execute only through `mf query`. | Static review and CI tripwire find no raw SQL execution path. |
| TR3 | Reject unknown metrics before execution. | `HallucinationChecker` blocks unknown metrics. |
| TR4 | Handle ambiguous questions without guessing. | `ambiguous` is distinct from unknown metric and system error; when at least two governed interpretations are valid, the response carries a bounded clarify payload, and a valid reply continues to MetricFlow. |
| TR5 | Reject unsupported domains. | Customer-service questions return `unsupported_domain`. |
| TR6 | Resolve relative time against current date. | Hardcoded reference date is replaced by real clock plus test seam. |
| TR7 | Validate dimensions server-side. | Metric and dimension selections are checked against the semantic manifest before execution. |
| TR8 | Keep LLM provider pluggable. | Ollama, OpenAI-compatible, and Anthropic paths are config-driven; broken Anthropic signature is fixed before claiming support. |
| TR9 | Log every request for audit/eval. | JSON Lines log records question, category, metric, time window, command, elapsed time, and no credentials. |
| TR10 | Treat zero-row results as valid answers. | Empty MetricFlow rows return `answered`, not rejection. |
| TR11 | Meet latency target. | 95th percentile supported-question response is under 30 seconds. |
| TR12 | Use five outcome categories; `answered` additionally carries an additive `investigation` block and `ambiguous` may carry a bounded clarify payload (see TR12.1–TR12.9). | Five categories present (`answered`, `unknown_metric`, `ambiguous`, `unsupported_domain`, `system_error`); `unknown_metric`, `unsupported_domain`, and `system_error` keep their existing shapes; `ambiguous` is non-terminal only when catalog-grounded choices exist; the `investigation` key is present **iff** `category == "answered"`. |

### TR12 Outcome Contract — additive `investigation` extension (one-way door; 8.DECISION_LOG.md #13/#14)

TR12 is extended to ratify, at the response-contract level, the agentic investigation loop approved at gate-2 (design in `docs/6.DETAILED_DESIGN.md` §"Agentic Investigation Loop + Evidence-from-Governed-Data") and the clarify-and-continue contract for FR4a/FR4b. This subsection is the authoritative contract; `05` is the producing design. The extensions are additive to their owning categories — no existing key is removed, renamed, retyped, or given new semantics.

**Wording reconciliation (parked backlog item, 8.DECISION_LOG.md #8):** an earlier reading treated the scored guardrail bar as "category routing." The enforced/scored bar is **metric selection within the `answered` category** (NFR "Metric-routing correctness"); the five-way **category routing** is the outer classification, scored separately (8.DECISION_LOG.md #8/#8b). Both are measured; they are different bars, not the same one.

**TR12.1 — Additive `investigation` block on `answered`.** An `answered` response gains one object:
`investigation { status, steps_taken, stopped_reason, trace[], evidence[] }`.
- `status` — enum, required: `investigated` (loop reached synthesis with no mid-loop tool/infra failure; every warranted drill either produced evidence or cleanly abstained) | `partial` (a step failed or was cut off, so some warranted evidence is missing; carries an honest note; **never** a fabricated fill-in) | `not_investigated` (trigger classified the question as a plain lookup; loop did not fire — TR12.5).
- `steps_taken` — integer ≥ 0, required: count of governed `GovernedMetricTool` calls beyond the base answer (drills). `not_investigated` ⇒ `0`.
- `stopped_reason` — enum, required when `status ∈ {investigated, partial}`, `null` when `status == not_investigated`: `bounds` (`MAX_STEPS`/`MAX_DEPTH` reached) | `abstain` (next warranted drill abstained and nothing else warranted) | `repeat` (visited-signature loop-guard refused a duplicate and nothing else warranted) | `latency` (cumulative TR11 deadline reached — TR12.6) | `no_warranted_follow_up` (loop found no further governed drill worth running) | `error` (an internal exception aborted the investigation; the base metric answer still returned unchanged — floor-preservation path). Precedence when several apply in the terminating step: `latency` > `bounds` > `repeat` > `abstain` > `no_warranted_follow_up`.
- `trace[]` — ordered array, required (may be empty). Each record: `step` (1-based int), `intent` (the structured tool intent: `metric`, `group_by[governed dims]`, `time_window`, optional `rank`, optional `filters`), `category` (the **real** TR12 category of that step's governed result — abstained/failed branches carry their true `unknown_metric`/`ambiguous`/`unsupported_domain`/`system_error`, never a masked `answered`), `produced_evidence` (bool). `not_investigated` ⇒ `[]`.
- `evidence[]` — array, required (may be empty), records defined in TR12.3. `not_investigated` ⇒ `[]`.

**TR12.2 — Non-answer categories never carry investigation state.** `unknown_metric`, `unsupported_domain`, and `system_error` keep their existing keys and never carry `investigation`. `ambiguous` never carries `investigation`; when and only when the ambiguity has at least two catalog-valid branches, it may add the FR4a fields defined in TR12.9.
- *Mechanism.* Enforcement: the serializer attaches `investigation` only on the `answered` path. Adoption: all five categories serialize through that one boundary. Inspection: schema tests assert `("investigation" in response) == (category == "answered")`; clarify tests assert every `ambiguous.choices[].metric` exists in the served catalog.

**TR12.3 — Every `evidence[]` record is correlational, governed, and traceable; causation is structurally unrepresentable.** Each record MUST carry: `relationship` (const `"correlation"`), `governed` (const `true`), `source_tool_call_step` (int index into `trace[]`), and `claim_type` (closed enum defined by the EvidenceBundle in `05` §5.2 — currently `movement | dimensional_contribution | time_localization | coincident_signal`). Measured payload fields (delta, `share_of_total_delta`, coincident values) are the data-architect's EvidenceBundle (`05` §5.2), referenced not redefined here. **No causal field exists** and none may appear: the record schema has no key that could carry a cause, and the forbidden-key set `{cause, causes, caused_by, driver, drivers, reason, because, why}` must be absent from every evidence record.
- *Mechanism (not intention).* Enforcement: the evidence schema requires the four keys as `const`/typed, has no cause-bearing field, and CI rejects any evidence record missing a required key or containing a forbidden key. Adoption: every evidence record is emitted only by the EvidenceBundle serializer; no node writes evidence directly. Inspection: a per-record contract test asserts `relationship=="correlation"`, `governed==true`, `source_tool_call_step` resolves to an existing `trace[]` step, and no forbidden key is present; the post-synthesis causal-language linter (`05` §governance-4) scans the narrative for cause verbs and downgrades to correlational or fails synthesis toward abstention. "Structurally unrepresentable" is testable: there is no schema path that serializes a cause, so a test that greps the full `answered` payload for any forbidden key must find none across the entire eval set.

**TR12.4 — Abstained and failed drill branches never fabricate.** A drill whose governed result is non-`answered` (off-catalog metric/dimension, ambiguous, unsupported, or infra error) appears in `trace[]` with its real category, contributes **nothing** to `evidence[]`, and spawns no children (abstain-terminates-branch, `05` §loop-bounds). A mid-loop failure sets `status:"partial"` with an honest note, never a synthesized number.
- *Mechanism.* Inspection: an eval row that forces a drill to abstain asserts the branch is present in `trace[]` with the correct non-`answered` category, adds zero `evidence[]` records, and yields `status ∈ {investigated, partial}` with `stopped_reason ∈ {abstain, ...}` — and that no evidence record cites that step.

**TR12.5 — Trigger rule (Decision 1 = A): investigative intent only.** The loop fires only on **investigative intent**; plain lookups keep today's single-shot shape and return `investigation.status:"not_investigated"` with `steps_taken:0`, `trace:[]`, `evidence:[]`.
- *Definition (classifiable).* An **investigative intent** asks for explanation, decomposition, or attribution of a metric *movement or difference*: surface markers include "why did X change", "what drove/caused Y", "break down / decompose Z", "what explains", "which {accounts|models|regions} contributed", or an explicit comparison-with-explanation ("why is X higher than Y"). A **plain lookup** requests a metric value or list at a slice with no explanation request ("what was X last month", "top N by Y"). The classifier that decides this is owned by ai-architect (task 5.4); this TRD defines the two output shapes and the safety property, not the classifier's accuracy bar.
- *Safety property (testable, and why misclassification is non-catastrophic).* A **false negative** (investigative question routed as lookup) degrades gracefully to today's correct `answered` shape — less rich, still governed and correct. A **false positive** (lookup routed as investigative) still returns a correct `answered`: the base metric answer is the guaranteed floor, and the loop stops immediately with `stopped_reason:"no_warranted_follow_up"` when no governed drill is warranted. Eval: a labeled trigger set asserts lookups yield `not_investigated` (or an empty-evidence `investigated`) and investigative questions that are governed-decomposable yield non-empty `evidence[]`.

**TR12.6 — Investigation runs under the TR11 latency budget with bounded steps.** Cumulative wall-clock for base + all drills MUST stay within TR11 (30 s p95). Steps are bounded: `MAX_STEPS = 6` (1 base + ≤ 5 drills), `MAX_DEPTH = 3` (`05` §loop-bounds). The loop checks a cumulative deadline before each drill and, if the budget would be exceeded, terminates with `status:"partial"`, `stopped_reason:"latency"` rather than overrunning.
- *Mechanism.* Inspection: the TR11 p95 measurement includes investigative questions; a test with an injected slow tool asserts the loop returns `partial`/`latency` before the deadline instead of exceeding it.

**TR12.7 — Door classification and versioning/compat.** This contract change is a **one-way door** (8.DECISION_LOG.md #14): once clients depend on the response shape it is expensive to reverse. Compatibility story for a client pinned to the current TR12 shape:
- The change is a backward-compatible **minor** revision: new keys appear only inside `answered`, and every previously documented key keeps its name, type, and meaning. A client that reads only `category / metric / value / dimensions / time_range / rows` and **ignores unknown keys** keeps working with no change.
- The one known break is a client doing **strict schema validation that rejects unknown keys**; such a client must opt into the extended `answered` schema. This is the only non-graceful compat case and is flagged as the residual one-way-door risk.
- No top-level `contract_version` field is added, because a top-level field would touch all five categories and add churn outside the owning extension surfaces. Any future version marker MUST live inside the additive `investigation`/`answered` region, inside the additive `ambiguous.continuation` region, or wait for a deliberate major-version break. The TR12.2/TR12.9 tests are the mechanism that keeps the response contract from silently drifting.

**TR12.8 — Launch gates for the extension.** Before the investigation extension ships: (a) TR12.2 response-contract tests prove non-answer responses carry no `investigation`; (b) the TR12.3 evidence contract test and the causal-language linter run in CI and fail on a seeded causal-key/cause-verb row; (c) the TR12.4 never-fabricate eval passes on forced-abstain and mid-loop-failure rows; (d) TR11 p95 including investigative questions is under budget; (e) a rollback path exists (the loop is gated behind the TR12.5 trigger, so disabling the trigger reverts every response to today's single-shot shape).

**TR12.9 — Clarify-and-continue for `ambiguous` (FR4a/FR4b).** An `ambiguous` response may add `clarifying_question`, `choices[]`, and `continuation` when every offered choice is a governed catalog metric. Each `choices[]` record carries `id`, `metric`, `label`, and `domain`; `metric` MUST be present in the served catalog. `continuation` is client-carried stateless context: `{type:"metric_clarification", version:1, original_question, selection, choices, rounds_remaining:0}`. A follow-up `/query` request MAY send `{question:<reply>, continuation:<that object>}`; the backend deterministically maps the reply to exactly one offered choice and then executes MetricFlow using the original selection context plus the chosen metric.
- *Bounds.* Exactly one clarify round is allowed. A reply that maps to zero choices returns `unknown_metric` with reason `invalid_clarification_reply`; a reply that maps to multiple choices returns terminal `ambiguous` with reason `clarification_reply_ambiguous`; neither response emits a new `continuation`.
- *Mechanism.* Enforcement: choice construction filters against the served catalog; continuation resolution revalidates the chosen metric before execution and never trusts client-provided metrics beyond the normal TR3 guard. Adoption: `/query` is the only entry point for initial and follow-up turns. Inspection: unit tests cover grounded choice generation, invalid-branch decline, single-choice continuation to `mf query`, and no second continuation on bad replies.

## Non-Functional Requirements

| Requirement | Target |
|---|---|
| Latency | Under 30 seconds p95 for supported questions. |
| Metric-routing correctness | At least 95% on a domain-balanced eval set. |
| False rejection rate | 5% or lower for supported questions. |
| Auditability | Every answer traces to routing decision and `mf query`. |
| Extensibility | Adding a new governed domain or later agent loop should not require rewriting `/query`. |
| Security | No credentials in logs; synthetic data only in v1. |

## Integrations

| Integration | Contract | Failure Behavior |
|---|---|---|
| MetricFlow/dbt | Read-only local `mf query` subprocess. | Missing CLI, non-zero exit, or timeout returns `system_error`. |
| LLM provider | HTTP provider selected by config/request. | Provider error or malformed JSON returns `system_error`. |
| Semantic manifest/catalog | Local read-only generated artifacts. | Missing or stale catalog returns or logs `system_error`; rebuild when manifest mtime is newer. |
| Future RAG | Retrieval service over support tickets and feedback. | Retrieval supplies citations only; it never computes metrics. |

## Data Requirements

- Metrics and dimensions are defined only by MetricFlow semantic manifest.
- The manifest's metric YAML is generated from `seeds/metric_definitions_seed.csv`, the sole metric-authoring surface (GATE A 2026-07-06, 8.DECISION_LOG.md #1); the governed catalog is the 52-metric collapsed list in `docs/contracts/1.METRIC_DICTIONARY.csv`, with time grain and dimensional breakdown as query parameters rather than separate metrics.
- No service may introduce a metric or dimension outside the manifest.
- Quantitative values are measured MetricFlow outputs, never LLM-inferred values.
- Customer evidence RAG, when added, must index metadata that maps back to governed dimensions such as account, region, model family, segment, product area, and date.

## Security and Compliance

V1 uses synthetic data. No real customer PII is in scope. If real tickets, feedback, or customer records are introduced, privacy, retention, redaction, and account-level authorization must be reopened before build.

## Launch Gates

- Metric routing eval reaches target correctness.
- Rejection categories are scored separately.
- Unknown metrics and invalid dimensions are blocked before execution.
- Reference date and Anthropic BYOK defects are fixed.
- Structured logs exist and exclude credentials.
- Operational runbook and health checks exist.
- Investigation extension gates (TR12.8) are green: non-answer responses carry no `investigation`, evidence contract test + causal-language linter run in CI, never-fabricate eval passes, TR11 p95 holds with investigative questions, trigger-off rollback verified.
