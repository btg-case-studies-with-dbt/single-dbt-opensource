# Bedrock vs Open-Source — Component Comparison

**Product:** Governed Metric Execution Architecture for Agentic BI
**Status:** Reference
**Date:** 2026-07-08

## Purpose

Maps each AWS Bedrock managed component to the open-source alternative used or recommended in this project, so readers can evaluate tradeoffs.

| Layer | Bedrock (AWS Managed) | Open-Source Alternative | This Project Uses |
|---|---|---|---|
| **LLM inference** | Bedrock Claude / Titan / Llama via InvokeModel API | Ollama (local), OpenAI-compatible, Anthropic Direct API | Ollama default, BYOK config |
| **Model gateway** | Bedrock Cross-Region Inference / Bedrock Agents | LiteLLM Proxy | Config-driven provider dispatch in `llm_client.py` |
| **Agent runtime** | Bedrock Agents (built-in orchestration) | LangGraph | LangGraph (future — not yet implemented) |
| **RAG / retrieval** | Bedrock Knowledge Bases | LlamaIndex or Haystack | LlamaIndex/Haystack (future — not yet implemented) |
| **Vector store** | OpenSearch Serverless (Bedrock KB default) | pgvector or Qdrant | pgvector (future — Postgres already deployed) |
| **Guardrails** | Bedrock Guardrails (built-in content filters) | Guardrails AI / NeMo Guardrails / Presidio | Deterministic validators + HallucinationChecker |
| **Tool execution** | Bedrock Action Groups | FastAPI tools or MCP servers | FastAPI endpoints (`/query`, `/catalog`, `/health`) |
| **Evaluation** | Bedrock Model Evaluation (eval jobs) | Ragas, DeepEval, promptfoo | Domain-balanced eval suite (planned) |
| **Observability** | CloudWatch + Bedrock model invocation logs | OpenTelemetry + Langfuse | JSON Lines audit log to `evidence/` |
| **Embeddings** | Bedrock Titan Embeddings / Cohere Embed | sentence-transformers, OpenAI embeddings | Not yet selected (future RAG layer) |
| **Data ingestion** | Bedrock KB Sync (S3 → OpenSearch) | Airbyte, Meltano, Airflow | Airflow (existing DAGs) |
| **Deployment model** | AWS-hosted (managed infra, pay-per-token) | Local Docker Compose / self-hosted | Local Docker Compose (this project) |
| **Key management** | AWS KMS (integrated with Bedrock) | Environment-variable / config-driven BYOK | `LLMConfig.from_env()` in `llm_client.py` |

## Key Tradeoffs

| Dimension | Bedrock | Open-Source |
|---|---|---|
| **Setup time** | Minutes (API calls) | Hours (infrastructure, config) |
| **Cost model** | Pay-per-token, no infra management | Free inference (Ollama) or BYOK per-token |
| **Data privacy** | Data processed on AWS (see Bedrock data policy) | Fully local — no data leaves the machine |
| **Latency** | Network-dependent (single-digit ms to seconds) | Local: near-zero (Ollama); BYOK: same as Bedrock |
| **Model choice** | Limited to Bedrock-supported models | Any model (Ollama), any provider (BYOK) |
| **Offline capability** | No (requires AWS network) | Yes (local Ollama) |
| **Vendor lock-in** | High (Bedrock Agents, KB, Guardrails are proprietary) | None (each component swappable) |
| **Scaling** | AWS-managed auto-scaling | Manual (single-user local in this project) |

## Architecture Note

In this project's architecture, Bedrock would replace the **LLM provider slot** only. All other layers — metric governance (dbt + MetricFlow), server-side validation, the five-category response contract, and the future RAG boundary — remain the same regardless of whether the LLM comes from Bedrock, Ollama, or a BYOK provider. The `llm_client.py` provider-agnostic dispatch is designed to make this swap a config change, not a code change.
