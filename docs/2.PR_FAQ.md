## Press Release

### Headline

AI-inference teams can ask one question and get one governed answer across revenue, usage, and capacity.

### Sub-Headline

The architecture routes natural-language analytics through dbt and MetricFlow, then leaves room for customer evidence RAG without letting an LLM generate raw SQL.

### Summary

AI-inference businesses run on signals that live across teams. Finance owns revenue. Engineering owns usage, quota, and capacity. Customer-facing teams see support tickets and feedback. When these signals disagree, teams spend time reconciling definitions before making a decision.

This project demonstrates a safer agentic BI architecture. Quantitative answers are executed only by the governed semantic layer. The LLM selects from approved metrics and dimensions, the backend validates the selection against the semantic manifest, and MetricFlow runs the query. Future RAG retrieves customer support tickets and feedback as cited qualitative evidence, not as a query engine.

### Problem

The hard part is not adding chat to analytics. The hard part is preventing a model from becoming the source of truth. Cross-domain language is ambiguous: "requests" can mean API requests, quota requests, or support requests. "Usage" can mean tokens, model utilization, customer activity, or spend. A fast answer is dangerous if it silently chooses the wrong metric.

### Solution

The system uses a governed metric execution path:

1. Natural-language question enters the FastAPI service.
2. The LLM maps it to an approved metric, dimension, and time range.
3. The backend validates the metric and dimensions against the semantic manifest.
4. MetricFlow executes the governed query.
5. The UI returns an answer or a specific rejection category.

The future agentic BI path keeps a clean split:

- **MetricFlow/dbt:** quantitative truth.
- **RAG over tickets and feedback:** qualitative evidence.
- **LLM/agent:** routing, planning, and synthesis inside enforced boundaries.

### Getting Started

This is a local case-study prototype. A reviewer starts the Docker Compose stack, builds the dbt project, validates MetricFlow, starts the conversational BI API, and asks a supported question such as "What was total net revenue last week?" or "Show total API requests by model type this quarter."

### Call To Action

Use the project as an inspectable engineering architecture reference for governed agentic BI. If the metric exists, the system answers through MetricFlow. If the metric or domain is unsupported, it rejects clearly. If customer evidence is needed, it belongs in a separate RAG layer with citations.

## External FAQ

### What is this?

An engineering architecture case study for governed agentic BI on synthetic AI-inference platform data.

### How is it different from a dashboard?

A dashboard expects the user to know where to look. This system routes a natural-language question to the correct governed metric and returns a traceable result.

### How is it different from text-to-SQL?

The LLM never writes warehouse SQL. It selects from governed metrics and dimensions. MetricFlow owns execution.

### Where does RAG fit?

RAG retrieves customer support tickets, feedback, call notes, and issue records as qualitative evidence after or alongside governed metric results. RAG does not execute analytics.

### Which domains are supported now?

Revenue, token usage, and quota/capacity. Customer-service questions are intentionally rejected until that domain has governed metrics.

### Does it answer "why" questions?

Not in the v1 governed-query path. Multi-step "why" investigations are reserved for the later LangGraph agent loop.

## Internal FAQ

### Why now?

The semantic layer already exists: Postgres, dbt medallion models, 11 semantic models, and 69 governed metrics across three domains. The next challenge is making those metrics usable through natural language without weakening governance.

### What is the make-or-break assumption?

The model can route cross-domain language to the correct governed metric at a 95% or better correctness bar on a domain-balanced eval set.

### What could make this fail?

- The eval set underrepresents quota, token usage, or ambiguous "requests" language.
- The app answers unsupported questions instead of rejecting them.
- Infrastructure errors are counted as product rejections.
- RAG evidence is allowed to imply quantitative claims unsupported by MetricFlow.
- Customer-service capability is marketed before the evidence model and retrieval layer exist.

### What claims are not yet allowed?

- Production readiness.
- Real customer-data readiness.
- ROI or productivity claims beyond measured local eval results.
- Customer-service BI coverage.
- Multi-step root-cause analysis.
- Any claim that the LLM can generate or validate SQL.
