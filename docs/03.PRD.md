# Product Requirements Document: Governed Metric Execution Architecture

**Status:** Draft for review
**Owner:** Product
**Date:** 2026-07-02
**Source inputs:** Consolidated from the project product notes into the canonical documentation chain.

## Problem Statement

RevOps, finance, engineering capacity, and customer-facing teams need trusted answers across revenue, token usage, quota, and later customer evidence. Today those answers require dashboard hopping and manual reconciliation. V1 proves the narrowest trustworthy path: a natural-language question answered by exactly one governed MetricFlow metric.

## Goals

- Answer one natural-language business question with one governed metric value.
- Execute every answer only through MetricFlow.
- Support the built domains: revenue, token usage, and quota/capacity.
- Reject unknown, ambiguous, or unsupported-domain questions instead of guessing.
- Resolve relative time ranges against the real current date.
- Keep the LLM provider pluggable and BYOK.
- Leave a clean future seam for customer evidence RAG and LangGraph investigations.

## Non-Goals

- Raw SQL generation.
- Automatic metric creation.
- Multi-step agent investigations in v1.
- Open-ended, multi-turn conversational dialogue or agentic back-and-forth. A single **bounded** clarify round is specified for clarify-and-continue (FR4a/FR4b); anything beyond one round stays out.
- Root-cause narratives or synthesized explanations across multiple metrics in v1.
- Customer-service metric answers before customer-service metrics exist.
- Production SaaS deployment, pricing, packaging, or public launch claims.

## Clarify-vs-Decline Decision Rule (governs FR4/FR4a/FR4b)

The line is drawn by **how many governed interpretations exist**, not by how the question is worded. Clarify only toward interpretations that exist and are answerable; never toward a decline.

| Situation | Governed interpretations that resolve | Outcome |
|---|---:|---|
| Exactly one governed metric + valid dimensions + resolvable time, **or** a documented default applies (e.g. "revenue" → `total_net_revenue`). | 1 | `answered` — answer directly, no question. |
| Two or more governed interpretations are each individually valid; choosing one requires a guess; **every** offered choice exists in the catalog. | 2+ | `ambiguous` → **clarify** (ask, then continue). |
| Domain is supported but no governed metric expresses the ask (e.g. "recurring revenue", "input-token cost"). | 0 | `unknown_metric` — decline, honestly. |
| Subject area has no governed metrics at all (headcount/HR, support tickets). | 0 | `unsupported_domain` — decline. |
| Infrastructure failure. | n/a | `system_error` — never a product decline. |

**Load-bearing rule:** never ask a clarifying question whose every branch leads to a decline. If disambiguation cannot land on a governed answer, decline immediately — an honest "I can't answer that" beats a question that wastes a turn and then declines anyway. Ambiguity means "which of these real answers?", not "maybe there's an answer."

## What a Good Clarifying Question Looks Like

A good clarifying question is a **bounded menu grounded in the catalog**, not a vague "please clarify." It:

1. Names the single most decision-relevant axis of ambiguity (metric vs. aggregation vs. dimension vs. time grain) — the one that most changes the answer — rather than enumerating every axis at once.
2. Offers **2–4 mutually exclusive choices**, each phrased in business language and each mapped to a real governed metric or query parameter.
3. Offers **no choice that does not exist** in the governed catalog.
4. Includes a sensible default the user can accept in one word ("…or I can show total tokens consumed by model, all-time").
5. Carries enough state that a short reply completes the original question.

**Worked example — "which deployment used the most tokens":** this carries three independent ambiguities against the catalog — metric (`total_tokens_consumed` vs `total_input_tokens` vs `total_output_tokens`), aggregation of "most" (sum over the window vs peak-minute `peak_tpm`), and "deployment" as a dimension (by model vs by region). Good behavior: resolve the highest-impact axis first, e.g. *"By 'most tokens' do you mean (a) total tokens consumed over a period, (b) the single busiest minute (peak TPM), or (c) input vs output tokens? And should I break it down by model or by region?"* — every option maps to a governed metric/dimension. Bad behavior: *"Your question is ambiguous, please rephrase."*

## Clarify-and-Continue Requirement Detail (PRD-Detail for FR4a/FR4b)

Per-requirement acceptance conditions, edge cases, degradation, data touched, and constraints. This deepens FR4a/FR4b; it adds no requirement beyond them.

**Trigger detection (FR4/FR4a).**
- Fires only when ≥2 governed interpretations resolve (per the Decision Rule). Single-axis and multi-axis ambiguity both trigger; multi-axis resolves the highest-impact axis first.
- Does **not** fire when a documented default resolves the question confidently — that is `answered`, not a clarify.
- Time-grain-only ambiguity ("most tokens" with no period) is a valid trigger on its own.

**Clarifying-question content (FR4a).**
- 2–4 enumerated choices; each maps to a governed metric or query parameter; each stated in business language; a one-word-acceptable default is offered.
- The choice set is proposed by the LLM but **validated server-side against the semantic manifest** before it is shown — same enforcement tenet as metric selection (prompts are hints, the server enforces). A proposed choice not in the manifest is dropped; if fewer than two valid choices remain, the system declines rather than asks.

**Degradation behavior (FR4b).**
- Reply selects a valid choice → answer the disambiguated question through MetricFlow (`answered`).
- Reply is still ambiguous → decline (do not ask again).
- Reply maps to a metric that does not exist → `unknown_metric`.
- Reply is off-topic / unsupported domain → `unsupported_domain`.
- User abandons the turn → terminal, no state retained beyond the session bound.
- Exactly one clarify round in all paths; no loop.

**Data touched.**
- Read-only: governed metric list, dimensions, and time grains from the semantic manifest/catalog (the choice source of truth).
- New: short-lived session/thread state to carry the original question across the clarify round. *(The mechanism for this state — session model, storage, and the `/query` contract change from single-shot to multi-turn — is the Software/Solutions Architect's to design, not specified here.)*
- Audit log (FR9) extends to record the clarify event, the offered choices, and the branch the user chose, excluding credentials.

**Constraints.**
- Governance is never weakened to enable clarification: every offered choice comes from the manifest.
- The latency target (Success Metrics) applies to the final answer after the reply, measured from the reply, not across the human's thinking time.
- The response-contract change (making `ambiguous` non-terminal, adding a clarifying-question payload and a follow-up affordance) alters TR12/TR4, a one-way door once clients depend on the five-category enum. That contract edit is owned by the Solutions Architect (already routed in DECISION_LOG #8) and is not made in this PRD.

## Open Risks

- The ambiguity boundary is now specified by the Clarify-vs-Decline Decision Rule; the make-or-break assumption for FR4a is that the LLM can propose a *bounded, catalog-valid* choice set for a genuinely ambiguous question — if it cannot, clarify-and-continue collapses back to decline and the increment has no payoff.
- Over-clarification risk: a system that asks when it could answer is a new failure mode (the analog of false rejection); the False Clarification Rate metric guards it.
- Scope/sequencing (recommendation, human decides via TPM): clarify-and-continue is a genuine multi-turn capability (stateful `/query`), not a prompt tweak, so it is recommended as a **named follow-on increment after the current metric-selection fix banks its clean baseline** — not a rider on it. Optional early value with no multi-turn cost: in the current increment, have an `ambiguous` result already **emit the catalog-grounded clarifying-question text** as an explanatory (still terminal) payload; this turns "I refuse" into "I'd need to know X — here are the choices," delivers most of the analyst's felt value cheaply, and produces the exact artifact the follow-on eval will grade.
- The eval set could overrepresent revenue and underrepresent quota or token usage.
- The current customer-service/RAG layer is not implemented.
- Anthropic BYOK and hardcoded reference-date defects are called out in architecture docs.
- If real customer data is introduced, security and privacy requirements must be reopened.
