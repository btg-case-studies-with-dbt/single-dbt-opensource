# Product Requirements Document: Governed Metric Execution Architecture

**Status:** Draft for review
**Owner:** Product
**Date:** 2026-07-02
**Source inputs:** Consolidated from the project product notes into the canonical documentation chain.

## Problem Statement

RevOps, finance, engineering capacity, and customer-facing teams need trusted answers across revenue, token usage, quota, and later customer evidence. Today those answers require dashboard hopping and manual reconciliation. V1 proves the narrowest trustworthy path: a natural-language question answered by exactly one governed MetricFlow metric.

## Goals

- Answer one natural-language business question with one governed metric value.
- Execute every answer only through MetricFlow.
- Support the built domains: revenue, token usage, and quota/capacity.
- Reject unknown, ambiguous, or unsupported-domain questions instead of guessing.
- Resolve relative time ranges against the real current date.
- Keep the LLM provider pluggable and BYOK.
- Leave a clean future seam for customer evidence RAG and LangGraph investigations.

## Non-Goals

- Raw SQL generation.
- Automatic metric creation.
- Multi-step agent investigations in v1.
- Root-cause narratives or synthesized explanations across multiple metrics in v1.
- Customer-service metric answers before customer-service metrics exist.
- Production SaaS deployment, pricing, packaging, or public launch claims.

## Functional Requirements

| ID | Requirement | Acceptance Condition |
|---|---|---|
| FR1 | Accept a natural-language question and return one governed metric value with dimensions and time range. | Supported questions return metric name, value, resolved time range, and requested breakdown with no SQL generated. |
| FR2 | Execute every answer through MetricFlow. | Every answer traces to an `mf query`; no code path constructs raw SQL for user questions. |
| FR3 | Reject unknown metrics. | Unknown metrics return a clear `unknown_metric` outcome before execution. |
| FR4 | Reject ambiguous questions. | Ambiguous wording returns `ambiguous`, not a guessed metric or follow-up dialogue. |
| FR5 | Reject unsupported domains. | Customer-service questions return `unsupported_domain` until governed metrics exist. |
| FR6 | Resolve relative time from the real current date. | "Last week" and similar phrases are computed from actual request time, not a hardcoded date. |
| FR7 | Restrict dimensions to the semantic model. | Invalid dimensions are rejected or omitted before execution; none are invented. |
| FR8 | Support provider-agnostic LLM configuration. | Local and BYOK providers can be swapped by config without code changes. |
| FR9 | Log question, routing decision, outcome category, and time window. | Each request produces an audit/eval record that excludes credentials. |

## Success Metrics

| Metric | Baseline | Target | Instrument |
|---|---:|---:|---|
| Time to answer | Estimated 8-10 minutes for routine manual flow | Under 30 seconds | API timing |
| Metric-routing correctness | Not formally measured | At least 95% | Domain-balanced eval set |
| False rejection rate | Not formally measured | 5% or lower for supported questions | Eval set |
| Rejection-category accuracy | Not formally measured | TBD at launch gate | Rejection eval categories |
| Cross-domain coverage | Revenue, token usage, quota built | All built domains represented | Eval fixture inventory |

## Open Risks

- The ambiguity boundary is not yet fully specified.
- The eval set could overrepresent revenue and underrepresent quota or token usage.
- The current customer-service/RAG layer is not implemented.
- Anthropic BYOK and hardcoded reference-date defects are called out in architecture docs.
- If real customer data is introduced, security and privacy requirements must be reopened.

## Future Work

1. Customer evidence RAG for support tickets and feedback.
2. LangGraph multi-step agent investigations.
3. Stronger observability and evals for metric-plus-evidence synthesis.
4. Production identity, authorization, and deployment design.
